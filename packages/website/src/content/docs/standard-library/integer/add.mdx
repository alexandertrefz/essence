`add` is an overload set rather than one method. Which member runs is decided
at compile time by the argument's type, and that choice is also what fixes the
return type — so the exactness is not a promise made at runtime, it is the
signature.

There is no implicit conversion anywhere in it. An `Integer` added to a
`Rational` does not become a `Rational` by being rounded into one; the sum is
held as a fraction because a fraction is what can hold it.

The parameter is unlabelled — that is what the `_` in the signature means, and
why the call reads `2::add(3)` rather than `2::add(other 3)`.

## Returns

The type of the argument, in every case: `Integer + Integer` is an `Integer`,
and each of the three wider types comes back as itself.

That is the whole rule, and it is worth saying what it rules out. The result is
never a floating point number, because essence has none. It is never truncated
to fit a machine word, because an `Integer` has no width. And it is never a
union you have to take apart afterwards — the overload that ran already decided
which single type you are holding.

## Examples

The two common cases. `add` on two Integers is closed; a Rational argument
widens the result, and narrows again if the denominator cancels.

```essence
implementation {

	§ Integer + Integer stays an Integer.
	Terminal.print(2::add(3)::toString()) § "5"

	§ Integer + Rational widens to a Rational — the sum need not be whole.
	Terminal.print(2::add(1/2)::toString()) § "5/2"

	§ Three tenths, added exactly. Nothing rounds on the way, so the
	§ denominator cancels and the answer narrows back to a whole number.
	constant total = 1/10::add(2/10)::add(7/10)
	Terminal.print(total::toString()) § "1/1"
}
```

The irrational members behave the same way. Adding an `Integer` to `π` shifts
the rational part and leaves the π term alone, which is why the result can be
printed exactly rather than as a decimal approximation of it:

```essence
implementation {

	§ Number.Pi is a Transcendental. The π term survives the addition.
	Terminal.print(2::add(Number.Pi)::toString()) § "2 + π"
}
```

An `Algebraic` reaches you through an `Optional`, because the root it came from
might not have existed. Take the `Optional` apart with one `match` and the
union inside it with another, and the branch that holds a number can add to it:

```essence
implementation {

	§ squareRoot answers an Optional — a negative Integer has no real root —
	§ and its value is an Integer when the root is whole, an Algebraic when
	§ it is not.
	constant root = 2::squareRoot()

	constant shifted = match root -> String {
		case #Empty { <- "no root" }
		case #Value(value) {
			<- match value -> String {
				case Integer { <- 1::add(@)::toString() }
				case Algebraic { <- 1::add(@)::toString() }
			}
		}
	}

	Terminal.print(shifted) § "1 + √2"
}
```

<Note>
	`Integer`, `Rational`, `Algebraic` and `Transcendental` each carry their own
	same-kind arithmetic. A receiver whose type is a single member reaches its
	own namespace first, so `2::add(3)` never walks the cross-kind table on
	`Number`.
</Note>
