`Integer` has no methods. Neither has `String`, nor `List<T>`, nor any record
shape you write. A type here describes values and nothing else; everything you
can ask a value is declared separately, in a `namespace`, and attached to the
type from the outside. `2::add(3)` works because a namespace called `Integer`
declares `add` for the type `Integer` — and that namespace is written in
essence, in a file you can read.

## The double colon

A function is reached by its name and reads inwards. A method is reached
through `::` on a receiver and reads outwards, each answer becoming the next
receiver.

```essence
implementation {

	§ A Function is reached by its name, and reads inwards.
	function secondsUntilNoon(_ time: Integer) -> Integer {
		<- 43_200::subtract(time)
	}

	§ A Method is reached through `::` on a receiver, and reads outwards —
	§ each answer is the next receiver.
	Terminal.print(secondsUntilNoon(41_400)::quotient(dividingBy 60)) § 30

	Terminal.print(
		["apple", "cherry", "banana"]::sort()::lastItem()::otherwise("")::uppercase(),
	) § CHERRY
}
```

The two are not spellings of one thing. A function is a name bound in a scope;
a method is a name looked up in whichever namespaces target the receiver's
type. So a function is not reachable through `::`, and the compiler says where
it looked before giving up:

```
[unknown-method]
Error: No Method named 'secondsUntilNoon' for this value
   ╭─┤ chain.es:7:25 │
   │
 7 │     Terminal.print(41_400::secondsUntilNoon())
   │                    ───┬──  ────────┬───────  
   │                       ╰────────────│───────── this is an Integer
   │                                    │         
   │                                    ╰───────── no Method of this name
   │ 
   │ Note: Searched Namespaces 'Integer', 'Number'.
───╯
```

</div>

Two namespaces were searched for one `Integer`, which is this whole page in
miniature: there is no single place a type's methods live.

## A namespace for a type you do not own

`namespace X for T` declares methods for `T`. `T` need not be a type this file
wrote, and there is no permission to ask — `Integer` belongs to the standard
library, and a namespace of yours sits beside the library's own without
touching it. Inside a body, `@` is the receiver: the value the method was
called on.

```essence
implementation {

	§ An amount of money is a count of cents, and a count of cents is an
	§ Integer. The Namespace is where that reading lives.
	namespace Money for Integer {
		euros() -> Integer {
			<- @::quotient(dividingBy 100)
		}

		cents() -> Integer {
			<- @::remainder(dividingBy 100)
		}

		§ A Method of the same Namespace is reached on `@` like any other.
		formatted() -> String {
			<- "{@::euros()}.{@::cents()::toString()::pad(to 2, with "0")} EUR"
		}
	}

	Terminal.print(1234::euros()) § 12
	Terminal.print(1205::formatted()) § 12.05 EUR
}
```

The name in front of `for` is the namespace's own; the type after it is the
target. The two coincide often enough — the library writes `namespace Integer
for Integer` — that it is worth saying plainly that they are unrelated. `Money`
is what the reading is called, `Integer` is what it reads.

<Note>
	`@` is the same sigil a match arm uses for its subject and a refinement uses
	for the value under test. It always means "the value this construct is
	about", and it is never a name you can rebind.
</Note>

## Structural targets

A target need not be a name at all. Write a record shape and every record of
that shape answers — whoever wrote it, and whatever else it carries.

```essence
implementation {

	§ The target can be a Record shape rather than a name — any Record with
	§ these two fields answers `total`, whoever declared it.
	namespace Invoice for { subtotal: Integer, tax: Integer } {
		total() -> Integer {
			<- @.subtotal::add(@.tax)
		}
	}

	§ Neither of these was ever said to be an invoice, and the second
	§ carries a field the target does not mention.
	constant hosting = { subtotal = 1_200, tax = 228 }
	constant coffee = { subtotal = 350, tax = 24, note = "flat white" }

	Terminal.print(hosting::total()) § 1428
	Terminal.print(coffee::total()) § 374
}
```

This follows from records being
[structurally typed](/docs/language/records-and-lists): nothing declares a
record to be an `Invoice`, so there is nothing for a method to attach to except
the shape itself.

## Members that belong to the namespace

A `static` member belongs to the namespace rather than to any value, and is
reached with a dot on the namespace's name. A namespace that leaves out `for`
targets no type at all, so everything in it is static — which is how the
library's `Terminal` is built, and how a bag of related constants is written.

```essence
implementation {

	§ A Namespace with no `for` targets no Type at all, so nothing in it is
	§ ever reached on a value.
	namespace Currency {
		static symbol = "EUR"
	}

	namespace Money for Integer {
		§ `of` belongs to Money itself: it builds an amount rather than
		§ answering a question about one.
		static of(euros: Integer, and cents: Integer) -> Integer {
			<- euros::multiply(with 100)::add(cents)
		}

		formatted() -> String {
			<- "{@::quotient(dividingBy 100)} {Currency.symbol}"
		}
	}

	Terminal.print(Currency.symbol) § EUR
	Terminal.print(Money.of(euros 12, and 34)) § 1234
	Terminal.print(Money.of(euros 12, and 34)::formatted()) § 12 EUR
}
```

A static has no receiver, and so has no `@`: writing one inside a static body is
refused as `at-in-static-method`. Reaching for a static through `::` is refused
from the other side, as `static-method-on-value` rather than quietly
reinterpreted, and that diagnostic writes out the call that was meant.

## Choosing between namespaces

Any number of namespaces may target the same type, so a call has to pick one.
Three things decide it.

**The arguments.** A name shared by two namespaces is no conflict at all when
only one of them accepts what the call passes.

```essence
implementation {

	§ Both declare `scaled`, and the Argument settles which is meant.
	namespace Whole for Integer {
		scaled(by factor: Integer) -> Integer {
			<- @::multiply(with factor)
		}
	}

	namespace Exact for Integer {
		scaled(by factor: Rational) -> Rational {
			<- @::multiply(with factor)
		}
	}

	Terminal.print(1234::scaled(by 2)) § 2468
	Terminal.print(1234::scaled(by 1/4)) § 617/2
}
```

Within a single namespace the same job is done by an `overload` block, which
gathers several signatures under one name. Across namespaces it falls out of
the lookup, with nothing to declare.

**The narrower target.** Where two targets both cover the receiver and one of
them covers the other, the narrower one wins. A union target covers each of its
members, so a namespace for a member beats a namespace for the union.

```essence
implementation {

	§ A Namespace targeting a Union covers every member of it …
	namespace Amount for Integer | Rational {
		formatted() -> String {
			<- "{@} units"
		}
	}

	§ … and one targeting a single member is narrower, so an Integer never
	§ reaches the covering Namespace.
	namespace Cents for Integer {
		formatted() -> String {
			<- "{@::quotient(dividingBy 100)} EUR"
		}
	}

	constant share: Rational = 3/4

	Terminal.print(1234::formatted()) § 12 EUR
	Terminal.print(share::formatted()) § 3/4 units
}
```

The same order settles a record target against a wider one, and a
`List<Integer>` against a `List<ItemType>`. It is not a convenience: the
standard library rests on it. `Number` targets the union of the whole numeric
tower and `Integer` targets `Integer`, so two integers compare through
`Integer`'s own comparison rather than through the tower-wide one that would
otherwise have to answer.

**The call, saying so.** When neither the arguments nor the targets separate
the candidates, the call is refused as `ambiguous-namespace`, with one note per
namespace that declares the name. The answer is to write the namespace into the
call, between the `::` and the method:

```essence
implementation {

	§ Two readings of one and the same Integer — a count of cents as an
	§ amount, and as a line of a ledger.
	namespace Money for Integer {
		formatted() -> String {
			<- "{@::quotient(dividingBy 100)} EUR"
		}
	}

	namespace Accounting for Integer {
		§ Inside a body the question is the same one, so the answer is too.
		formatted() -> String {
			if @::isNegative() {
				<- "({@::absolute()::<Money>formatted()})"
			} else {
				<- @::<Money>formatted()
			}
		}
	}

	constant refund = 0::subtract(1234)

	Terminal.print(1234::<Money>formatted()) § 12 EUR
	Terminal.print(refund::<Accounting>formatted()) § (12 EUR)
}
```

`::<Money>formatted()` is an ordinary method call with the ambiguity taken out
of it, and it is worth writing even where a bare call would resolve — when the
reading is the point. `refund::<Accounting>formatted()` says which convention
the line is written in, and goes on saying it after somebody adds a third.

## The standard library is namespaces, and nothing else

Every method on this page is a namespace member declared in essence.
`Integer.es` declares `namespace Integer for Integer is Equatable, is
Printable, is Comparable`; `Number.es` covers the union the whole numeric tower
is named by, `Integer | Rational | Irrational`; `Terminal` has no `for` and
holds only statics. The `is` clauses declare
[protocol](/docs/language/protocols) conformance, which is a second thing a
namespace does and no part of what makes its methods reachable.

Nothing there is privileged. The library's namespaces are found by the lookup
above, ordered by the specificity above, and disambiguated by the syntax above,
so a chain crossing between the library and your own file has no seam in it —
`Number.sum([1_200, 599, 25])::formatted()` is a library static followed by a
method of your own, and there is nothing in the chain that could tell you so.

That is the consequence worth keeping: extending a type you did not write is
not an escape hatch bolted on beside the real mechanism. It is the mechanism,
and the library uses it on its own types exactly as you use it on theirs.
