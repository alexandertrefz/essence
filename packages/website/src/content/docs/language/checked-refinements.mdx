`NonZeroInteger` is not a naming convention. It is a type every value of which
has been proven not to be zero, and the proof is what the type carries: a value
nobody has asked the question of is not one of its values, and the compiler
says so rather than trusting the name. That is the whole of a checked
refinement — a base type, a predicate, and evidence that the predicate holds.

What it is for is the operation that can then stop apologising. Division by a
proven divisor cannot fail, so it answers a `Rational` instead of an
`Optional<Rational>`; a list proven to have something in it has a first item, so
`firstItem` answers an item. The fallback does not disappear — it moves to the
one place that genuinely needs it, in front of the branch rather than after
every call.

## Declaring one

A `where` clause on a type alias declares a refinement. `@` stands for the value
being refined, and the clause is a question asked of it.

```essence
implementation {

	§ A String with something in it.
	type NonEmptyString = String where @::hasAnyContent()

	§ A List with something in it. The base is an APPLIED List — never a bare
	§ `List`, whose item Type nothing has decided.
	type NonEmptyStrings = List<String> where @::hasItems()

	§ `isBetween` is not Integer's own — it is declared once over the whole
	§ numeric tower, and the predicate records the Namespace that answered it.
	type Digit = Integer where @::isBetween(0, and 9)

	§ The predicates are ordinary Methods, and answer here about ordinary
	§ values nobody is proving anything about.
	Terminal.print("essence"::hasAnyContent()) § true
	Terminal.print(["a", "b"]::hasItems()) § true
	Terminal.print(7::isBetween(0, and 9)) § true
}
```

Three bases may be refined: `Integer`, `String` and an applied `List` —
`List<String>` or `List<Item>`, never a bare `List` whose item type nothing has
decided. The predicate is nothing special in itself: `hasAnyContent`,
`hasItems` and `isBetween` are the same methods any expression may call, and
asking one of an ordinary value is an ordinary question that answers `true` or
`false`. What the `where` clause does is promise that the answer has already
been `true` for every value the type admits.

## What the predicate may say

The predicate is one method call on `@` — or several joined with `::and(…)` —
and its arguments are written out as literals. A name will not do, even a
constant one:

<div class="error-output">

```
[invalid-refinement-predicate]
Error: This is not a predicate a refinement can be checked by
   ╭─┤ bounded.es:5:45 │
   │
 5 │     type Bounded = Integer where @::isLessThan(limit)
   │                                                ──┬──
   │                                                  ╰──── this is not a literal value
   │
   │ Help: Pass a written Integer, Rational, String or Boolean.
   │
   │ Note: A predicate is one Method call on '@' with literal Arguments, or several of them joined with '::and(…)'.
───╯
```

</div>

The restriction is the price of the property that makes refinements worth
having: the compiler compares two of them by what they **prove**, not by how the
proof was spelled. A predicate is stored as a set of resolved method calls —
the method and the entry of it that answered, the namespace that answered it,
the literal arguments — rather than as the text that was written, and two
refinements holding the same set are the same type. A name in argument position
would have to be compared as an expression, and two expressions that mean the
same number are not a question a type system can settle.

Four other shapes are refused for the same reason, all of them under
`invalid-refinement-predicate`.

- A clause that is not a method call at all, such as a name standing on its own.
- A receiver that is not `@`. The clause is evidence about the value being
  refined, and about nothing else.
- A chained receiver, such as `@::trim()::hasAnyContent()`. The evidence would
  be about the intermediate value, which nothing has proven anything about.
- A base outside the three above.

A clause that answers something other than a boolean — `where @::absolute()` —
is `predicate-not-boolean` instead.

What that buys is that a refinement belongs to nobody. A program's own alias and
the standard library's are one type whenever they prove the same thing of the
same base:

```essence
implementation {

	§ Two refinements proving the same thing of the same base are ONE Type,
	§ however each was spelled.
	type NonEmptyStrings = List<String> where @::hasItems()

	function lengthOf(_ items: NonEmptyStrings) -> Integer {
		<- items::length()
	}

	§ So a value of the standard library's `NonEmptyList<String>` is accepted
	§ by a Function asking for this Program's own.
	constant colours: NonEmptyList<String> = ["red", "green", "blue"]

	Terminal.print(lengthOf(colours)) § 3
	Terminal.print(lengthOf(colours::reverse())) § 3
}
```

## Conjunctions

`::and(…)` joins predicates, and the chains flatten — so a conjunction and its
mirror image prove the same two things and are therefore the same type.

```essence
implementation {

	§ `::and(…)` chains flatten, so this proves two things — and the mirror
	§ image of it proves the same two. The two Aliases are one Type.
	type SmallOdd = Integer where @::isOdd()::and(@::isLessThan(10))

	type OddAndSmall = Integer where @::isLessThan(10)::and(@::isOdd())

	function tripled(_ n: SmallOdd) -> Integer {
		<- n::multiply(with 3)
	}

	§ A conjunction establishes any refinement asking for SOME of what it
	§ proves, and where several qualify the one proving the most wins.
	function scaledOdd(_ n: Integer) -> Integer {
		if n::isOdd()::and(n::isLessThan(10)) {
			<- tripled(n)
		}

		<- 0
	}

	constant seven: OddAndSmall = 7

	Terminal.print(tripled(seven)) § 21
	Terminal.print(scaledOdd(7)) § 21
	Terminal.print(scaledOdd(8)) § 0
}
```

Because a predicate is a set, establishing one is set inclusion: proving two
things establishes every refinement asking for some of them, and where several
qualify at once the one proving the most wins.

## Evidence adds, and never takes anything away

A refinement is its base plus a promise, so it answers everything its base
answers, and it flows back into its base wherever a base is expected. Forgetting
a proof loses nothing; the other direction is the one that needs evidence, which
is the point of the type.

```essence
implementation {

	§ Evidence ADDS to a Type and never takes anything away, so a
	§ NonZeroInteger answers every Method an Integer answers …
	function doubled(_ n: NonZeroInteger) -> Integer {
		<- n::multiply(with 2)
	}

	§ … and flows into its base for free. Forgetting a proof loses nothing;
	§ the other direction is the one that needs evidence, which is the point
	§ of the Type.
	function forgotten(_ n: NonZeroInteger) -> Integer {
		<- n
	}

	Terminal.print(doubled(21)) § 42
	Terminal.print(forgotten(21)) § 21
}
```

## Three ways a value gets in

Handing a refinement a value nothing has proven anything about does not compile,
and the diagnostic names the predicate that was not established along with both
routes through it:

<div class="error-output">

```
[argument-type-mismatch]
Error: This Argument does not fit Parameter 1
   ╭─┤ doubled.es:9:14 │
   │
 9 │        <- doubled(n)
   │                   ▲
   │                   ╰── this is an Integer
   │
   │ Help: Check '@::isNot(0)' on the value in an 'if' or a 'match', or pass a value that already has Type 'NonZeroInteger'.
   │
   │ Note 1: Parameter 1 is NonZeroInteger.
   │ Note 2: Every value of 'NonZeroInteger' has been proven to answer '@::isNot(0)'.
───╯
```

</div>

### A value written down

A literal is its own evidence. Its predicate is decided while compiling, so no
branch stands in front of it and nothing has asked anything at runtime — which
holds wherever a refinement is expected: a declared constant, a returned value,
an argument.

```essence
implementation {

	function doubled(_ n: NonZeroInteger) -> Integer {
		<- n::multiply(with 2)
	}

	§ A value written DOWN is its own evidence: the predicate is decided
	§ while compiling, so nothing has asked anything.
	constant twentyOne: NonZeroInteger = 21

	§ Which holds wherever a refinement is expected — a declared Constant, a
	§ returned value, an Argument.
	function three() -> NonZeroInteger {
		<- 3
	}

	Terminal.print(doubled(twentyOne)) § 42
	Terminal.print(doubled(three())) § 6
	Terminal.print(doubled(21)) § 42
}
```

Those three are the whole of it, and receiver position is not among them: a
refinement is expected where a type was declared, and nothing declares the type
of a receiver. `["a", "b"]::firstItem()` answers `List`'s own `Optional`
however plainly the brackets say the list has something in it — the value has
to be standing somewhere a refinement was asked for before being written down
counts as evidence.

### An `if` that asks the question

An `if` whose condition asks a refinement's question narrows the constant it
asked it of. That is what makes a doorway writable: a bare value goes in, and
the branch that proved the predicate is the only one that reaches the operation
demanding the proof.

```essence
implementation {

	type NonEmptyString = String where @::hasAnyContent()

	function doubled(_ n: NonZeroInteger) -> Integer {
		<- n::multiply(with 2)
	}

	function exclaimed(_ text: NonEmptyString) -> String {
		<- text::append("!")
	}

	§ A bare Integer comes in, and the branch that proved the predicate is
	§ the only one that reaches `doubled`.
	function doubledOrZero(_ n: Integer) -> Integer {
		if n::isNot(0) {
			<- doubled(n)
		}

		<- 0
	}

	§ The `else` branch narrows too, through the opposite Method: a String
	§ that is not empty has content.
	function shout(_ text: String) -> String {
		if text::isEmpty() {
			<- "…"
		} else {
			<- exclaimed(text)
		}
	}

	Terminal.print(doubledOrZero(21)) § 42
	Terminal.print(doubledOrZero(0)) § 0
	Terminal.print(shout("essence")) § "essence!"
	Terminal.print(shout("")) § "…"
}
```

Note which branch of `shout` does the proving. Asking `isEmpty` narrows the
`else`, because a string that is not empty has content — and that is why the
standard library declares those questions in pairs, `isEmpty` beside
`hasAnyContent` and `isEmpty` beside `hasItems`. Either arm can be the one that
establishes something, so the condition can be written the way the code reads
best rather than the way the proof demands.

### A match over a bare value

A match on a bare integer or string takes the **value** apart, and its cases are
evidence in both directions. A case that names a value proves that value; the
case answering for the rest is reached only by a value none of the cases above
it named — which is the very `isNot` a `NonZeroInteger` is declared by. This is
a doorway nobody has to write.

```essence
implementation {

	type Zero = Integer where @::is(0)

	type Digit = Integer where @::isBetween(0, and 9)

	function named(_ zero: Zero) -> String {
		<- zero::toString()
	}

	function doubled(_ n: NonZeroInteger) -> Integer {
		<- n::multiply(with 2)
	}

	function placed(_ digit: Digit) -> Integer {
		<- digit::add(1)
	}

	§ A Case that NAMES a value proves it, and reaching `case _` proves the
	§ value is none of the values the Cases above it named.
	function doubledOrNamed(_ n: Integer) -> String {
		<- match n -> String {
			case 0 { <- named(@) }

			case _ { <- doubled(@)::toString() }
		}
	}

	§ A Guard proves things about `@` the same way, and it runs before any
	§ Statement of the body.
	function digitOrZero(_ value: Integer | String) -> Integer {
		<- match value -> Integer {
			case Integer where @::isBetween(0, and 9) { <- placed(@) }

			case _ { <- 0 }
		}
	}

	Terminal.print(doubledOrNamed(21)) § "42"
	Terminal.print(doubledOrNamed(0)) § "0"
	Terminal.print(digitOrZero(7)) § 8
	Terminal.print(digitOrZero("seven")) § 0
}
```

The two mechanisms in that sample are worth telling apart. `doubledOrNamed`
proves its refinements out of the shape of the match itself, with no predicate
written anywhere; `digitOrZero` writes one, as an arm's guard, and a guard runs
before any statement of the arm's body, so what it proves is in hand for the
whole of it.

## What the standard library's two buy

The standard library declares exactly two refinements, and each exists to remove
an `Optional` that stood for a case which cannot arise.

### `NonZeroInteger`, and division that cannot fail

`type NonZeroInteger = Integer where @::isNot(0)` is the refinement the design
was written for. `Integer::divide(by:)` has an entry for a possibly-zero divisor
that answers `Optional<Rational>`, and an entry for a proven one that answers
the `Rational` itself — there is no failure left to report.

```essence
implementation {

	§ A written 4 is its own proof, so this division can not fail and the
	§ quotient itself is the answer.
	constant exact: Rational = 12::divide(by 4)

	§ A divisor nothing has vouched for still answers the Optional it always
	§ has.
	function shareOfMaybe(_ total: Integer, sharedBy people: Integer) -> Optional<Rational> {
		<- total::divide(by people)
	}

	§ And an `if` that asks the question hands the branch a proven divisor —
	§ the Optional goes away with the case it stood for.
	function shareOf(_ total: Integer, sharedBy people: Integer) -> Rational {
		if people::isNot(0) {
			<- total::divide(by people)
		}

		<- 0/1
	}

	Terminal.print(exact) § 3/1
	Terminal.print(shareOfMaybe(12, sharedBy 5)) § Value(12/5)
	Terminal.print(shareOfMaybe(12, sharedBy 0)) § Empty
	Terminal.print(shareOf(12, sharedBy 5)) § 12/5
	Terminal.print(shareOf(12, sharedBy 0)) § 0/1
}
```

`divide(by:)` is not alone in the shape. `quotient(dividingBy:)` and
`remainder(dividingBy:)` are split the same way — an `Optional<Integer>` over a
divisor nothing is known about, the integer itself over a proven one — and
`Rational.of(_:over:)`, the one gateway a `Rational` may be built by, asks for a
proven denominator rather than reporting a failure nobody could act on.
`Rational::denominator` answers a `NonZeroInteger` in turn, which is what lets
arithmetic over the lowest-terms accessors compose without a single fallback for
a case that cannot arise.

One operation keeps the evidence rather than forgetting it:
`NonZeroInteger::multiply(with:)` takes a proven factor and answers a proven
product, because a product is zero exactly when one of its factors is, so
neither factor being zero is the whole of the proof. It is the only one that
closes — a sum of two non-zero integers is `1` and `0 - 1`, and a difference is
the same.

### `NonEmptyList`, and `firstItem` that answers an item

`type NonEmptyList<ItemType> = List<ItemType> where @::hasItems()` is the other,
and the generic one. Whether a list has items is not a question about what it
holds, so one predicate serves every item type and the type argument lives in
the base — a `NonEmptyList<String>` and a `NonEmptyList<Integer>` are told apart
exactly as `List<String>` and `List<Integer>` are.

```essence
implementation {

	§ A List nothing has proven anything about answers the Optional it
	§ always had …
	constant unproven = ["essence", "language"]

	§ … while one carrying the proof answers with the item itself.
	constant colours: NonEmptyList<String> = ["red", "green", "blue"]

	§ And the proof survives a transform that can not spend it, so a chain
	§ of them never asks again.
	Terminal.print(unproven::firstItem()) § Value(essence)
	Terminal.print(colours::firstItem()) § "red"
	Terminal.print(colours::sort()::firstItem()) § "blue"
	Terminal.print(colours::reverse()::lastItem()) § "red"

	§ Which puts the fallback in front of the branch rather than after the
	§ call.
	function firstWordOr(_ words: List<String>, _ fallback: String) -> String {
		if words::hasItems() {
			<- words::firstItem()
		}

		<- fallback
	}

	Terminal.print(firstWordOr(["essence", "language"], "none")) § "essence"
	Terminal.print(firstWordOr([], "none")) § "none"
}
```

Two things are going on there. `firstItem` and `lastItem` **spend** the proof:
a list with something in it has a first item and a last one, so no case is left
over for an `Optional` to stand for. `sort`, `reverse`, `map`,
`removeDuplicates`, `replace` and the two `contentsOf` growers **carry** it:
each answers with one item for every item it was handed — or one for every
distinct item, or those items and more besides — so none can
empty a list that was not empty, and each says so with a `NonEmptyList` where
`List`'s own entry says `List`. That is what keeps a chain of them from asking
`hasItems` again at every step.

Everything a proof does not survive keeps `List`'s own entry and costs the
proof. `keepEvery`, `removeEvery`, `slice`, `remove`, `removeFirst` and
`removeLast` can all answer empty from a receiver that was not; `flatten`
empties on a list of empty lists; `partition`, `pair` and `split` build lists
nobody has proven anything about; and `firstItem(where:)` may find nothing, so
it keeps the `Optional` its unfiltered namesake sheds. Reaching one of those is
what a later `hasItems` is for.

<Note>
	The single-item growers work the other way round: `append(_:)`,
	`prepend(_:)` and `insert(_:at:)` are declared on `List` itself and answer
	with a `NonEmptyList` whatever they were handed, since putting an item into
	any list makes a list with an item in it — and
	`List.of(integersFrom:through:)` hands one out the same way. That is a proof
	a program is given rather than one it has to take.
</Note>
