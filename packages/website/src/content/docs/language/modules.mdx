A program larger than a page wants to be more than one file, and there is one
way to split it: a file is a module, a module says what it publishes, and
another module asks for those names by the path to the file. There is no
manifest, no package registry and no search path — a specifier is a relative
path, so the file a line names can be found by anyone reading that line.

## The shape of a module

`implementation { … }` is still the body of a file. A module is that body with
up to two blocks around it: an `import { … }` before it, listing the names it
takes from elsewhere, and an `export { … }` after it, listing the names it
offers.

A file that needs nothing from anywhere writes no import block at all:

<CodeWindow
	title="Money.es"
	class="code-bare"
	compact
	code={`implementation {

	§ A Type, the Namespace that builds one, and a second Namespace that
	§ renders one. Only the names the export block lists leave this file.
	type Money = { cents: Integer }

	namespace Money for Money {
		static of(euros: Integer, cents: Integer) -> Money {
			<- { cents = euros::multiply(with 100)::add(cents) }
		}
	}

	namespace MoneyFormatting for Money {
		format() -> String {
			constant euros = @.cents::quotient(dividingBy 100)
			constant cents = @.cents::remainder(dividingBy 100)

			<- "{euros}.{padded(cents)}"
		}
	}

	§ An implementation detail: nothing outside this file can name it.
	function padded(_ value: Integer) -> String {
		<- value::toString()::pad(to 2, with "0", at #Start)
	}
}

export {
	Money
	MoneyFormatting
}`}
/>

Everything a module declares is private unless its export block names it.
`padded` is not on that list, so it exists for `format` and for nothing else —
asking for it from another file is refused, and refused with the reason rather
than with "no such name":

<div class="error-output">

```
[not-exported]
Error: 'padded' is not exported by ./Money.es
   ╭─┤ Main.es:2:2 │
   │
 2 │     padded from "./Money.es"
   │     ───┬──
   │        ╰──── declared in that Module, but private
   │
   │ Help: Add 'padded' to the 'export { … }' block of ./Money.es.
   │
   │ Note: A name is private unless the Module's 'export { … }' block lists it.
───╯
```

</div>

Functions, constants, type aliases, choices, protocols and namespaces can all
be exported. A variable cannot: a variable two files can both read is state
neither of them owns, and which of them wrote it last is not something either
one states. Declare it a constant, or export a function that answers with the
value.

## Asking for a name

An import block is one entry per line, and each entry carries its own `from`
clause:

<CodeWindow
	title="report/Report.es"
	class="code-bare"
	compact
	code={`import {
	Money           from "../Money.es"
	MoneyFormatting from "../Money.es"
}

implementation {

	function totalled(_ amounts: List<Money>) -> Money {
		<- { cents = Number.sum(amounts::map((item) { <- item.cents })) }
	}

	function summary(of amounts: List<Money>) -> String {
		<- "{amounts::length()} items, {totalled(amounts)::format()}"
	}
}

export {
	summary
}`}
/>

Repeating the specifier on every line is the point rather than an oversight. A
name and the file it came from are on one line, so reading an unfamiliar file
top to bottom never involves counting braces to work out which group a name
belongs to. There is no wildcard form, and nothing is brought in that was not
written down: what a module can see is the list, and the list is the whole of
it.

An entry binds its name in this module exactly as a declaration does. Two
entries therefore cannot share a name, and an entry cannot take a name
something else already holds — a builtin, a declaration in this file, an
earlier entry. Both are reported as `duplicate-import`, and the entry is
refused rather than allowed to shadow, so whatever held the name still means
what it did. `as` on the entry is the way through, which is the next section.

## A specifier is a path, and only a path

`"../Money.es"` is read exactly as written. It has to begin with `./` or `../`,
it has to end in `.es`, and it is resolved against the directory of the file it
is written in — never against the directory `essence` was invoked from, so a
Module means the same thing wherever the compiler is run and whatever the
editor's process happens to be rooted at.

Nothing is appended and no directory is searched. A bare name is not a package
lookup, because there is no package resolution to fall back to:

<div class="error-output">

```
[invalid-module-specifier]
Error: Module specifier 'Money' is not a relative path
   ╭─┤ Main.es:2:13 │
   │
 2 │     Money from "Money"
   │                ───┬───
   │                   ╰───── a specifier is a path relative to this Module
   │
   │ Help: Write the path from this Module to the file, beginning with './' or '../'.
   │
   │ Note: Package specifiers are reserved: today a Module names its dependencies by where they sit relative to it, and nothing is searched for.
───╯
```

</div>

An absolute path is refused for a different reason — it names a place on the
machine it was written on, so a checkout that moves stops compiling. A
specifier that resolves to the file it sits in is refused as `self-import`:
everything a module declares is in scope inside it already, exported or not.

## Renaming, and forwarding

`as` renames an entry. On an import it renames the name locally and leaves the
exporting module untouched; on an export it renames the name for everyone, and
an importer then has to ask for a name that appears nowhere in that file's
implementation.

An export entry with a `from` clause forwards a name without binding it here,
which is what makes a facade possible — one file that publishes a coherent
surface assembled out of several:

<CodeWindow
	title="Catalogue.es"
	class="code-bare"
	compact
	code={`import {
	Money from "./Money.es"
}

implementation {

	function discounted(_ price: Money, byPercent percent: Integer) -> Money {
		constant rate   = 100::subtract(percent)
		constant scaled = price.cents::multiply(with rate)

		<- { cents = scaled::quotient(dividingBy 100) }
	}
}

export {
	discounted
	Money           from "./Money.es"
	MoneyFormatting from "./Money.es"
}`}
/>

A re-export is a dependency like any other — the export block's `from` clauses
count towards the graph, so `Catalogue.es` depends on `Money.es` whether or not
its implementation names anything from it.

Importing `Money` through the facade and importing it straight from `Money.es`
answer the same type. A module is identified by the file it is, not by the
route taken to it, so `Report.es` above and `Main.es` below are talking about
one `Money`.

## Namespaces travel by name

The entry point of the program pulls all of it together — three names from the
facade, one from the report, one of them renamed on the way in:

<CodeWindow
	title="Main.es"
	class="code-bare"
	compact
	code={`import {
	Money                    from "./Catalogue.es"
	MoneyFormatting          from "./Catalogue.es"
	discounted               from "./Catalogue.es"
	summary as basketSummary from "./report/Report.es"
}

implementation {

	§ \`MoneyFormatting\` is never named below — \`::format()\` dispatches through
	§ it, which is what makes the entry a use rather than an unused import.
	constant basket = [Money.of(euros 4, cents 50), Money.of(euros 12, cents 5)]
	constant sale   = discounted(Money.of(euros 20, cents 0), byPercent 15)

	Terminal.print(sale::format()) § 17.00
	Terminal.print(basketSummary(of basket)) § 2 items, 16.55
}`}
/>

`MoneyFormatting` appears in the import block and nowhere else, and the entry
is doing real work: Method dispatch never crosses an import silently. Delete
that one line and `sale::format()` stops resolving — the compiler says so, and
says where the method it could not reach lives:

<div class="error-output">

```
[unknown-method]
Error: No Method named 'format' for this value
    ╭─┤ Main.es:14:23 │
    │
 14 │     Terminal.print(sale::format()) § 17.00
    │                    ──┬─  ───┬──
    │                      ╰──────│──── this is a { cents: Integer }
    │                             │
    │                             ╰──── no Method of this name
    │
    │ Help: 'MoneyFormatting' in ./Catalogue.es declares 'format' for { cents: Integer } — import it.
    │
    │ Note: Searched Namespaces 'Record', 'Money'.
────╯
```

</div>

This is the rule that keeps a call readable. If importing a type dragged in
every namespace anyone had ever written for it, what `::format()` resolved to
would be a function of some other file's export list, and a method could appear
or change meaning because a dependency grew one. Here, the namespaces in play
are the ones written in the block at the top of the file.

<Note>
	Where two imported namespaces both offer a method for the same value, the
	one that wins is decided in a canonical order — by specifier, then by the
	exported name, then by the local one — rather than by the order the entries
	were written in. That is the order `essence format` writes an import block
	in, so re-sorting a block can never change what a call resolves to.
</Note>

An import that genuinely goes unread is a Warning, `unused-import`, tagged so
an editor renders the line faded. A namespace counts as used the moment a
Method dispatches through it, even where the call never spells its name.

## The Prelude

`Integer`, `String`, `List`, `Optional`, `Terminal` — none of these were
imported anywhere above, and no program imports them. They come from the
standard library, and which of its names reach a program is decided by one
file:

<CodeWindow
	title="standard-library/sources/Prelude.es"
	class="code-bare"
	compact
	code={`declarations {}

export {
	Algebraic         from "./Algebraic.es"
	Boolean           from "./Boolean.es"
	Comparable        from "./Comparable.es"
	Integer           from "./Integer.es"
	NonZeroInteger    from "./Integer.es"
	List              from "./List.es"
	NestedList        from "./List.es"
	NonEmptyList      from "./List.es"
	loop              from "./Loop.es"
	Irrational        from "./Number.es"
	Number            from "./Number.es"
	NestedOptional    from "./Optional.es"
	Optional          from "./Optional.es"
	Ordering          from "./Ordering.es"
	Equatable         from "./Protocols.es"
	Printable         from "./Protocols.es"
	NumberFormat      from "./Rational.es"
	Rational          from "./Rational.es"
	Rounding          from "./Rational.es"
	Record            from "./Record.es"
	Step              from "./Step.es"
	Case              from "./String.es"
	NormalizationForm from "./String.es"
	Side              from "./String.es"
	String            from "./String.es"
	Stream            from "./Terminal.es"
	Terminal          from "./Terminal.es"
	Transcendental    from "./Transcendental.es"
}`}
/>

That is the file below its opening comment, and it is the whole public surface
of the language. `Prelude.es` declares nothing — `declarations { … }` is the
other body form, the one the standard library's own sources are written in,
where a declaration carries no body because the runtime implements it, and here
it is empty. The compiler builds its table of builtins out of that export block
alone.

Adding a name there adds it to the language; removing one takes it away. A name
that a standard library file exports and the Prelude does not forward is
reachable by the library's own sources and by nothing else — which is how the
library keeps an internal helper without the language growing a name for it.

The library's sources use `import { … }` and `export { … }` among themselves,
exactly as the files above do. What they are not is part of your graph: a
specifier that resolves into the standard library is refused, with the note
that the standard library is one shared declaration space rather than a graph
of modules and everything it publishes is in scope already. There is nothing to
import, and so no way to import it.

## When a module body runs

A module body runs once, the first time something reaches it, and dependencies
run before the modules that name them. The entry runs last, because everything
it reaches is something it depends on.

<CodeWindow
	title="Config.es"
	class="code-bare"
	compact
	code={`implementation {

	constant NAME = "essence"

	Terminal.print("Config.es ran")
}

export {
	NAME
}`}
/>

<CodeWindow
	title="Main.es"
	class="code-bare"
	compact
	code={`import {
	NAME from "./Config.es"
}

implementation {
	Terminal.print("Main.es ran, and NAME is {NAME}")
}`}
/>

Running `Main.es` prints `Config.es ran` and then
`Main.es ran, and NAME is essence`. A file reached by two importers still runs
once; the second one finds it already run.

## Cycles

Two modules are allowed to import each other. Declarations are hoisted — a
Function, a type alias, a choice, a protocol and a namespace are all in place
before any body runs — so a cycle over those is not a problem to be worked
around:

<CodeWindow
	title="Totals.es"
	class="code-bare"
	compact
	code={`import {
	rounded from "./Rounding.es"
}

implementation {

	§ The cycle is fine for everything that hoists: \`rounded\` is in scope
	§ here although Rounding.es imports \`Amount\` straight back.
	type Amount = { cents: Integer }

	function withTax(_ amount: Amount) -> Amount {
		<- rounded({ cents = amount.cents::multiply(with 119) })
	}
}

export {
	Amount
	withTax
}`}
/>

<CodeWindow
	title="Rounding.es"
	class="code-bare"
	compact
	code={`import {
	Amount from "./Totals.es"
}

implementation {

	function rounded(_ amount: Amount) -> Amount {
		<- { cents = amount.cents::quotient(dividingBy 100) }
	}
}

export {
	rounded
}`}
/>

A constant is the one thing a cycle cannot carry. Its value exists only once
its module's body has run, and inside a cycle there is no first body — which
one runs first is decided by the entry point rather than by any of the files
involved. Move `119` above into a `constant SCALE` in `Rounding.es` and import
it, and the compiler refuses the entry rather than letting the program read a
name that is not there yet:

<div class="error-output">

```
[cyclic-constant-import]
Error: Constant 'SCALE' is imported across a cycle
   ╭─┤ Totals.es:2:2 │
   │
 2 │     SCALE   from "./Rounding.es"
   │     ──┬──
   │       ╰──── this Constant is not readable here
   │
   │ Help: Move the Constant into a Module outside the cycle, or expose it as a Function.
   │
   │ Note 1: ./Rounding.es imports this Module back, directly or through further Modules.
   │ Note 2: A Function, a Type Alias, a Choice, a Protocol and a Namespace are all hoisted, so a cycle can name any of them. A Constant is not: its value exists only once its Module's body has run, and inside a cycle which body runs first is not something the source states.
───╯
```

</div>

The same reasoning makes a top-level statement inside a cycle a Warning rather
than an error. The program is well-formed; it is well-formed in more than one
way, and `cyclic-side-effects` names the other modules of the cycle and says
why the statement's position in the run is not something the source decides.

## Compiling a program of several files

Point the compiler at the entry. Everything it reaches is read, parsed and
checked with it — there is no file list to maintain, because the import blocks
already are one:

```sh
$ essence check Main.es
  ✔ Main.es no errors

    read      0.23 ms  ░
    parse      4.4 ms  █
    enrich      72 ms  ████████████████████████
    validate  0.19 ms  ░

    total   77 ms
```

The four modules are one run of the pipeline rather than four, which is why
there is one set of timings and not a table of them.

Naming several files checks each of them as an entry of its own, which is what
`essence check *.es` in a pre-commit hook is for: a file nothing imports yet
still gets checked. Each file is read and linked once for the whole invocation,
however many entries reach it.

```sh
$ essence check *.es report/*.es
  ✔ 4 files checked

    ✔ Catalogue.es         87 ms
    ✔ Main.es            0.46 ms
    ✔ Money.es           0.19 ms
    ✔ report/Report.es   0.17 ms

    4 files checked in 119 ms
```

`essence watch Main.es` watches the whole graph rather than the file it was
given, so editing `Money.es` rebuilds the entry that reaches it.

A build produces one file:

```sh
$ essence build Main.es
  ✔ Main.es → Main.js

    read      0.08 ms  ░
    parse      4.3 ms  █
    enrich      65 ms  ██████████████
    validate  0.20 ms  ░
    simplify  0.44 ms  ░
    optimise   6.8 ms  █
    generate   115 ms  ████████████████████████
    bundle      17 ms  ███
    write     0.48 ms  ░

    output  12.5 kB · 3.2 kB gzipped
    total   211 ms
```

`Main.js` holds all four modules and the parts of the essence runtime the
program actually reaches, with no `import` statement anywhere in it and nothing
to install beside it. Modules are a source-level organising tool: they decide
what a file may see and in what order bodies run, and then they are gone. Where
you drew the lines shows up in how the source reads, not in what ships.
