A `define` is a definition by cases. It is a list of arms, each one a value and
the condition that reaches it, and it answers with the value of the first arm
whose condition holds. The last arm is `otherwise`, and it holds when none of
the others did.

```essence
implementation {

	§ The arms are tried in the order they are written, and the `define`
	§ answers with the value of the first one whose Condition holds.
	function graded(_ score: Integer) -> String {
		<- define {
			as "top marks" if score::isGreaterThanOrEqualTo(90)
			as "a pass"    if score::isGreaterThanOrEqualTo(50)
			as "not yet"   otherwise
		}
	}

	Terminal.print(graded(95)) § "top marks"
	Terminal.print(graded(60)) § "a pass"
	Terminal.print(graded(10)) § "not yet"
}
```

A `define` is an expression rather than a statement, so it stands wherever a
value stands — what a function answers with, what a constant is bound to, an
argument, or another arm's value.

## Arms are tried in order

`graded(95)` answers both of the first two questions, and the one written above
decides. Reordering the arms is therefore a change of meaning wherever two of
the conditions can hold at once.

An arm below the `otherwise` arm can never run, because `otherwise` is the arm
that always holds. Move it above the last question and the arm under it is
refused rather than quietly dropped:

<div class="error-output">

```
[unreachable-define-arm]
Error: This arm stands below the 'otherwise' arm
   ╭─┤ graded.es:9:4 │
   │
 9 │          as "a pass"    if score::isGreaterThanOrEqualTo(50)
   │          ─┐
   │           ╰── nothing here can ever be reached
   │
   │ Help: Move this arm above the 'otherwise' arm, or delete it.
   │
   │ Note: The 'otherwise' arm is the one that always holds, so a 'define' answers there whenever it gets that far.
───╯
```

</div>

That refusal is about position, and only position. Whether two conditions
overlap is not something the compiler works out, so a ladder that asks the same
question twice compiles, and the arm the earlier one has already answered for
is dead code nothing points at.

## `otherwise` is not optional

Every other arm carries a condition, so a `define` without an `otherwise` arm
has nothing left to answer with when they all decline. Delete it and the
program does not parse:

<div class="error-output">

```
[define-without-otherwise]
Error: This 'define' has no 'otherwise' arm
   ╭─┤ graded.es:6:6 │
   │
 6 │ ╭─▶        <- define {
   ┆ ┆
 9 │ ├─▶        }
   │ │
   │ ╰────────────── every value here has a condition on it
   │
   │ Help: Write the last arm as 'as <value> otherwise'.
   │
   │ Note: A 'define' answers with a value wherever it stands, so one of its arms has to be the one that always holds.
───╯
```

</div>

That the parser refuses it, rather than the validator, is the point. There is
no node shape for a `define` with the arm missing, so every `define` the rest of
the compiler sees is total by construction — a `define` answers with a value
wherever it stands, and there is no falling off the end of one the way a
function body can fall off its own.

The arm that always holds is also the only one required. A `define` that has
nothing else is the value it answers with written the long way round, and is
reported as a warning rather than an error, because this is the shape a ladder
has while it is still being written:

<div class="error-output">

```
[define-without-cases]
Warning: This 'define' has no cases
   ╭─┤ tally.es:3:19 │
   │
 3 │ ╭─▶     constant tally = define {
   ┆ ┆
 5 │ ├─▶     }
   │ │
   │ ╰─────────── nothing here is decided by cases
   │
   │ Help: Write the 'otherwise' value on its own, or add the arms this 'define' was going to ask.
   │
   │ Note: A 'define' answers with the value of the first arm whose Condition holds — and the 'otherwise' arm is the one that holds when none of them did.
───╯
```

</div>

## An arm declares nothing and binds nothing

A `define` has no subject. There is no scrutinee for `@` to mean, no matcher to
write, and no name an arm brings into scope: an arm is two ordinary
expressions — the value, and the condition that reaches it — and each arm may
ask its question of a different value entirely.

```essence
implementation {

	§ A `define` has no subject: each arm asks its own question, of whatever
	§ value it likes.
	function statusOf(_ count: Integer, ready: Boolean) -> String {
		<- define {
			as "not started"     if ready::negate()
			as "nothing to do"   if count::isZero()
			as "{count} waiting" otherwise
		}
	}

	Terminal.print(statusOf(3, ready false)) § "not started"
	Terminal.print(statusOf(0, ready true)) § "nothing to do"
	Terminal.print(statusOf(3, ready true)) § "3 waiting"
}
```

Binding nothing is what keeps a `define` an expression rather than a second
spelling of `match`. Everything an arm says, it says about values that were
already in scope where the `define` was written.

## What an arm proves for the arms below it

An arm is reached only where every condition above it answered false, so the
complements of those conditions hold throughout it — and its own condition holds
throughout its value. That is an `else if` chain's rule, asked of a chain that
answers with values rather than with bodies, and it is read through the same
machinery an `if` narrows through. A condition asking a
[refinement](/docs/language/checked-refinements)'s question therefore
establishes that refinement for every arm below it.

```essence
implementation {

	§ An arm's own Condition holds throughout its value, so this divisor is
	§ proven where it is written.
	function shareOf(_ total: Integer, over count: Integer) -> Rational {
		<- define {
			as total::divide(by count) if count::isNot(0)
			as 0/1 otherwise
		}
	}

	§ And its complement holds for every arm below it, so the same division
	§ compiles under an arm that asked the opposite question.
	function shared(_ total: Integer, over count: Integer) -> Rational {
		<- define {
			as 0/1 if count::isZero()
			as total::divide(by count) otherwise
		}
	}

	Terminal.print(shareOf(12, over 4)) § 3
	Terminal.print(shareOf(12, over 0)) § 0
	Terminal.print(shared(12, over 4)) § 3
	Terminal.print(shared(12, over 0)) § 0
}
```

`shared` is the one worth reading twice. `count` arrives as a plain `Integer`,
and `Integer::divide(by:)` answers an `Optional<Rational>` for a divisor that
might be zero. The `otherwise` arm is reached only by a value that declined
`count::isZero()`, which is the very `@::isNot(0)` that `NonZeroInteger` is
declared by — so the division standing there is the entry that cannot fail, and
answers the `Rational` itself.

### A conjunction leaves nothing behind

A condition joined by `::and()` narrows its own arm by both halves and leaves
the arms below it nothing. A conjunction that answers false says one of its
questions failed and not which one, so there is no complement to hand down.
Widen the condition in `shared` and the division under it is the one that can
fail again:

<div class="error-output">

```
[return-type-mismatch]
Error: This arm does not answer with the Type this 'define' has
    ╭─┤ shared.es:17:7 │
    │
 17 │          as total::divide(by count) otherwise
    │             ───────────┬───────────
    │                        ╰───────────── this is an Optional<Rational>
    │
    │ Note: This 'define' answers Rational.
────╯
```

</div>

This is a fact about what a false answer proves rather than a limitation to
work around: a question that has to decide the arms below it goes on an arm of
its own.

## What a `define` answers with

Three things can decide the answer type, and they are asked in this order: the
arrow written on the `define` itself, the position the `define` stands in, and
— where neither of those said anything — the union of what the arms answer
with. Whichever of the first two spoke is pushed into every arm as that arm's
expected type, which is what lets an arm answering with a bare `#Empty` resolve
at all.

```essence
implementation {

	constant skipped = false

	function described(_ value: Integer | String) -> String {
		<- match value -> String {
			case Integer { <- "the Integer {@}" }
			case String  { <- "the String {@}" }
		}
	}

	§ The arrow is a claim about the `define` itself …
	constant fromArrow = define -> Optional<Integer> {
		as #Empty    if skipped
		as #Value(7) otherwise
	}

	§ … and the position it stands in is a claim about what may stand there.
	constant fromPosition: Optional<Integer> = define {
		as #Empty    if skipped
		as #Value(7) otherwise
	}

	§ Where neither says anything, the arms decide between them.
	constant fromArms = define {
		as "none" if skipped
		as 7      otherwise
	}

	Terminal.print(fromArrow) § Value(7)
	Terminal.print(fromPosition) § Value(7)
	Terminal.print(described(fromArms)) § "the Integer 7"
}
```

`fromArms` is the third case: nothing above it said anything, so its type is
the union of what its two arms answer with, and `String | Integer` is what
`described` takes. The other two are one type each, because the arrow and the
annotation were pushed into the arms before the arms were read — which is the
only reason a bare `#Empty` resolved in either.

Every arm is then held to whatever decided it, the `otherwise` arm among them.
An arm is what a `define` returns, so an arm answering with something else is
`return-type-mismatch` — the same code a `<-` gets, for the same reason.

An argument position is the one position that hands nothing down: a call picks
its overload by its arguments, so no parameter type is decided before the
arguments are read, and a `define` written straight into one has to write its
arrow. Where nothing decides at all, and the arms have nothing to take a union
of either, both halves of that are reported:


The arm's own diagnostic names the case and the type parameters left over; the
`define`'s names the construct that could have answered them, because the help
the first one offers — annotate the declaration — is one an argument position
does not have.

## `define` or `match`

A `match` takes a value apart by shape; a `define` picks by condition. What
separates them is whether the answer needs something the value was carrying: a
case matcher names a payload, and no arm of a `define` can name anything at all,
so whatever needs one stays a `match`.

```essence
implementation {

	choice Delivery {
		Pending,
		Shipped { days: Integer },
	}

	§ A `match` takes a value apart BY SHAPE, and a Case names the payload
	§ that shape carries.
	function etaOf(_ delivery: Delivery) -> String {
		<- match delivery -> String {
			case #Pending       { <- "not on its way yet" }
			case #Shipped(days) { <- "{days} days out" }
		}
	}

	§ A `define` picks BY CONDITION. It has no subject to take apart and no
	§ arm can name a payload, so anything needing one stays a `match`.
	function urgencyOf(_ days: Integer) -> String {
		<- define {
			as "late"  if days::isNegative()
			as "today" if days::isZero()
			as "soon"  if days::isLessThan(3)
			as "later" otherwise
		}
	}

	Terminal.print(etaOf(#Pending)) § "not on its way yet"
	Terminal.print(etaOf(#Shipped({ days = 2 }))) § "2 days out"
	Terminal.print(urgencyOf(-1)) § "late"
	Terminal.print(urgencyOf(0)) § "today"
	Terminal.print(urgencyOf(2)) § "soon"
	Terminal.print(urgencyOf(9)) § "later"
}
```

`urgencyOf` could not have been written as a `match` at all. A match over an
`Integer` takes the value apart, and is held to a shape when it does: every case
names a written value, and the last of them answers for every value the others
did not name. `days::isLessThan(3)` names no value, and a case that does name
one may not carry a guard either — so a ladder of ranges has nowhere to stand
inside one. The alternative is an `if`/`else if` chain, which is statements: it
answers with a value only by being a function body, and cannot stand where a
value stands.
