A language that compiles to JavaScript has an obvious way to disappoint you at
the debugger: you set a breakpoint on an Essence line, the program stops, and
the editor shows you generated code you did not write. That does not happen
here, and the reason is not clever. The compiler emits a real source map —
position by position, with your file named in it — and a debug session reads
that map in both directions. A breakpoint on a `.es` line is translated into a
position in the bundle before it is planted; every stop and every stack frame
is translated back before you see it. Names are undone the same way, by running
the compiler's own mangling rules backwards: a constant the emitter had to
spell `$user_ok_3f_` because JavaScript has no `?` in an identifier reads as
`ok?` again, and `_new` reads as `new`.

The session itself is a Debug Adapter. `essence dap` starts it, beside
`essence lsp`, and it speaks the Debug Adapter protocol over stdio to whatever
started it. At the other end it drives the compiled bundle under Node's own
inspector protocol. Your editor talks to one end, the running program to the
other, and the map is what keeps the two talking about the same file.

Two things follow from that, and both are worth knowing before you start. The
program runs under **Node** — the adapter speaks V8's inspector protocol, and
nothing else answers it. And the JavaScript a session debugs is not the
JavaScript `essence build` ships: the adapter compiles with the **optimiser
off**, because half the optimisation registry exists to delete exactly the
Statements, bindings and tests a debugger stops on.

Commands below are written as plain `essence`, which is what a global install
gives you; a project dependency takes your package manager's prefix in front,
and a checkout takes `bun run`.
[Installation](/docs/getting-started/installation) covers each way in.

<StepItem title="Have a program worth stopping in">

A debugger is wasted on a program with one statement. This one has a call, a
walk over a List and two Records to look at — enough that the stack has a
shape and the variables view has something to render.

<CodeWindow
	title="Weather.es"
	class="code-bare"
	compact
	code={`implementation {

	type Reading = { day: String, degrees: Integer }

	§ The warmer of two readings, keeping the one already held on a tie.
	function warmer(_ leader: Reading, _ reading: Reading) -> Reading {
		if reading.degrees::isGreaterThan(leader.degrees) {
			<- reading
		}

		<- leader
	}

	§ The warmest morning of a week, as a line to print.
	function warmest(_ readings: List<Reading>) -> String {
		constant coldest: Reading = { day = "none", degrees = 0 }

		constant best = readings::reduce(startingWith coldest, warmer)

		<- "{best.day} at {best.degrees}°"
	}

	constant week = [
		{ day = "Monday", degrees = 3 },
		{ day = "Tuesday", degrees = 9 },
		{ day = "Wednesday", degrees = 5 },
	]

	Terminal.print(warmest(week))
}`}
/>

<StepItem title="Look at what a breakpoint has to work with">

Nothing about the session is magic, and you can hold the ingredient in your
hand before you use it. `--sourcemap` writes the map beside the output, and
`--no-optimise` is what a debug session does for you:

```sh
$ essence build Weather.es --sourcemap --no-optimise
  ✔ Weather.es → Weather.js

    read      0.07 ms  ░
    parse      2.6 ms  █
    enrich      64 ms  ████████████████████████
    validate  0.06 ms  ░
    simplify  0.30 ms  ░
    optimise  0.69 ms  ░
    generate    48 ms  ██████████████████
    bundle      18 ms  ███████
    write     0.87 ms  ░

    output  8.0 kB · 2.2 kB gzipped
    total   135 ms
```

The map is a small file — under two kilobytes for this program — and its head
says what a session needs:

```json
{"version":3,"sources":["/Users/you/Weather.es"],"names":["reading","leader","readings","coldest","warmer","best","$es_Terminal_print__overload$1","warmest","week"],"mappings":";;;;;;;;;;;;;…
```

`sources` is your `.es` file under its canonical absolute path, `names` carries
the identifiers you wrote, and `mappings` is the position-by-position
correspondence. The adapter asks it two questions and only two: *where did this
source line land in the bundle*, which is how a breakpoint is planted, and
*where did this bundle position come from*, which is how a stop, a stack frame
and an exception's trace are read back. `sourcesContent` is in there too, so the
map is self-sufficient if the source ever moves.

Notice that the unoptimised bundle is the larger of the two — 8.0 kB against
the 4.5 kB the ordinary build produced above. That is the trade a debug session
makes on your behalf: a constant nothing reads survives so you can read it, a
Function passed to `reduce` stays a function instead of being written out where
it stood, and the stack you step through is the one your source describes. If
you want to know what an optimised build did instead, the
[Optimisations reference](/docs/reference/optimisations) names every pass.

<Note>
	Debugging never requires you to run this build yourself — a launch compiles
	into a scratch directory it deletes afterwards. Running it by hand is
	worth doing once, because everything the session does afterwards is
	explained by this file.
</Note>

</StepItem>

<StepItem title="Start a session in VS Code">

With the [VS Code extension](/docs/guides/editor-setup) installed, `F5` on an
open `.es` file is the whole ceremony. No `launch.json` is needed: the
extension notices that VS Code sent it an empty configuration, and builds one
out of the active editor — `type: "essence"`, `request: "launch"`, and
`program` set to the file you are looking at. The same entry appears in the
Run and Debug view's picker before any `launch.json` exists, so the two routes
cannot drift apart.

Two things have to exist on the machine, and neither ships with the extension:

- **The `essence` CLI**, because the adapter is the CLI's own `dap` command —
  the same binary that compiles a program is the one that debugs it, so the two
  can never disagree about a bundle or its map. The extension looks for it in
  three places, in order: the `essence.cli.path` setting, then
  `packages/cli/bin/essence` inside the workspace folder if you have a checkout
  open, then `essence` on PATH. Which one it picked is written to the `Essence`
  channel in the Output panel at every launch, as
  `Starting the Debug Adapter through the …`.
- **`node` on PATH**, because that is what runs the compiled program. Bun runs
  the compiler perfectly well and cannot run the debuggee: it has an inspector
  of its own, but not the one the adapter speaks. Setting
  `runtimeExecutable: "bun"` fails the launch after ten seconds with
  `'bun' announced no inspector endpoint within 10 seconds`.

If the program does not compile, the launch fails rather than starting
something stale. Each diagnostic arrives in the Debug Console on a line of its
own, under the path the launch named, with its position and its stable code;
the launch failure that follows names the file alone:

<div class="error-output">

```
/Users/you/Broken.es:3:30 — This value does not fit the declared Type of Constant 'degrees' [assignment-type-mismatch]

'Broken.es' did not compile — see the session output.
```

</div>

That is one line per diagnostic rather than the drawn span `essence check`
would give you, because the Debug Console is not a terminal the compiler owns.
The code is the same code, and [Diagnostics](/docs/reference/diagnostics)
explains it either way. Once a program does run, that same console is where its
own output arrives — what `Terminal.print` writes, and whatever the program
puts on standard error, with Node's inspector housekeeping kept out of it.

<Note>
	Debugging is unavailable in a workspace you have not trusted. That is VS
	Code's rule rather than the extension's — Restricted Mode blocks debug
	sessions outright — and it is why the language features are deliberately
	left on there while the workspace's own values for `essence.cli.path` and
	`essence.server.path` are ignored: each names an executable to spawn, and
	an untrusted repository should not get to choose it.
</Note>

</StepItem>

<StepItem title="Stop, and read the stop">

Click the gutter beside line 18 — `constant best = readings::reduce(…)` — and
launch. The breakpoint binds against the map before the program is allowed to
run, and a bound breakpoint is one the debugger can honour, not one it hopes
to.

A breakpoint that lands somewhere with no statement slides forward to the next
one that has, and the dot moves in the gutter to say so. Asked for lines 18, 13
and 5 in this file, the session answers 18, 16 and 7: line 13 is blank, so it
slides to `constant coldest` on 16, and line 5 is a `§` comment, so it slides
into `warmer` and lands on the `if` on line 7.

At the stop on line 18, the Call Stack view has two frames and both of them are
yours — a name and a position each:

```
warmest      Weather.es:18:3
Weather.es   Weather.es:29:17
```

Everything between them is gone. The bundle's own frames — the inlined runtime,
the dispatch trampolines, Node's module bootstrap — are classified as glue and
hidden, and a module's top level is named after its file, because that is what
it is. The rule is mechanical: a frame the map can place is yours; a frame it
cannot, but which carries a standard library method's emitted name, is the
library's and stays greyed out under its Essence spelling; everything else is
glue. Much of the library is inlined runtime rather than a named method, so in
practice most of what disappears is the library too. Break inside a function
the library called back — an `isWarm` handed to `keepEvery` — and the stack is
your handler over your module, with the walk between them folded away.

The variables view is where the map stops being the interesting part and the
value rendering takes over. The Local scope at line 18 holds two entries:

<div class="table-scroll">

| Name | Value |
| --- | --- |
| `readings` | `[ { day = "Monday", degrees = 3 }, … ]` |
| `coldest` | `{ day = "none", degrees = 0 }` |

</div>

Neither of those is a JavaScript object dumped to a string. They are rendered
inside the debuggee by the same rules `Terminal.inspect` follows, so a Record
reads as a Record, a String is quoted, a Rational is `3/4` and a case is
`Optional#Value(3)`. Long values are cut to one line with an ellipsis and the
whole thing is one round trip per container, not one per value. Expanding
`readings` gives its items under their indices — `0`, `1`, `2` — and expanding
`coldest` gives `day` and `degrees`; the compiler's own bindings are left out
of a scope, a parameter that bound no name has nothing to show and is left out
too, and the receiver a method is emitted with reads back as the `self` your
`@` means.

The Debug Console evaluates in the frame you have selected, and this is the one
place where the Essence surface stops. The console speaks **JavaScript over the
compiled frame**, which is documented rather than hidden:

<div class="table-scroll">

| Typed | Answer |
| --- | --- |
| `readings` | `[ { day = "Monday", degrees = 3 }, … ]` |
| `coldest.degrees` | `0` |
| `coldest.degrees::isEven()` | `SyntaxError: Unexpected token ':'` |

</div>

Results still render as Essence values, and a lone identifier the emitted
program binds under another spelling — `ok?`, or a name like `new` that
JavaScript reserves — is retried under its compiled name before the failure is
reported. Anything past a single identifier is JavaScript, and `::` is not.

</StepItem>

<StepItem title="Step">

Stepping is where a source map on its own would not be enough. One Essence line
is often several generated statements, and between any two of them sits the
runtime: a step that honoured every generated statement would walk you through
the prelude on the way from line 18 to line 7.

It does not, because the moment the bundle's script is parsed the session tells
V8 that every range the map does not cover is blackboxed, and V8 carries steps
over those ranges itself. What the map covers is your code. What it does not
cover is everything else. On top of that the adapter runs a small loop of its
own: a landing in unmapped ground is stepped onwards, and a step-over that
lands on the same source line it started from goes again.

From the stop on line 18, the three commands land here:

<div class="table-scroll">

| Command | Where it lands |
| --- | --- |
| **Step Into** | `warmer` at `Weather.es:7`, with `leader` and `reading` in Local |
| **Step Over** (from 7) | `Weather.es:8` — the `<- reading` inside the `if` |
| **Step Out** (from 8) | `warmest` at `Weather.es:20`, the interpolated return |

</div>

The first of those is worth pausing on. `reduce` is a standard library method,
and stepping into line 18 crosses it entirely to arrive in `warmer` — your
Function, called by library code, entered as if you had called it yourself. The
third is the mirror image: stepping out of `warmer` does not drop you back into
the middle of `reduce`, it returns you to `warmest` after the whole walk has
finished. Blackboxed code is passed through, not visited.

`stopOnEntry` is the same machinery applied to the start of the program. The
raw entry pause sits at the bundle's first statement, which is bootstrap nobody
wrote; with `stopOnEntry: true` the session steps through that before showing
you anything, and the first stop is the first statement your source contains —
line 23 here, `constant week`, because a `type` and two `function` declarations
execute nothing.

Run Without Debugging (`Ctrl+F5`) goes through the same adapter and the same
compile. Nothing pauses: no breakpoints are sent, exceptions do not break, and
`stopOnEntry` stands down for the session.

<Note>
	The manual step loop has a budget of fifty landings. A step that spends it
	stops where it is rather than running on, so a pathological case leaves you
	somewhere odd rather than losing your session.
</Note>

</StepItem>

<StepItem title="Write a launch configuration">

`F5` on the current file covers most of what you want, and the moment you want
arguments, an environment or a fixed entry point, write it down. The extension
contributes one request type, `launch`; there is no `attach`.

```json
{
	"type": "essence",
	"request": "launch",
	"name": "Debug Weather",
	"program": "${workspaceFolder}/Weather.es",
	"args": [],
	"cwd": "${workspaceFolder}",
	"stopOnEntry": false
}
```

Nine attributes exist, and that is all of them:

<div class="table-scroll">

| Attribute | Default | What it does |
| --- | --- | --- |
| `program` | `${file}` | The `.es` source file to compile and debug. |
| `args` | `[]` | Arguments passed to the program. |
| `cwd` | `${workspaceFolder}` | The working directory the program runs in. |
| `env` | `{}` | Environment variables set for the program. |
| `stopOnEntry` | `false` | Pause on the first statement the program's own source wrote. |
| `runtimeExecutable` | `"node"` | The executable that runs the compiled JavaScript. |
| `glueFrames` | `"hide"` | What becomes of compiler-generated stack frames: hidden, or `"subtle"` to show them greyed out. |
| `keepArtifacts` | `false` | Keep the compiled JavaScript and its map after the session, and say where they are. |
| `artifact` | — | A precompiled bundle to debug instead of compiling `program`. |

</div>

Three of them are for when the session itself is what you are suspicious of.
`keepArtifacts: true` leaves the scratch directory in place and prints where it
went, as `Compiled to /private/var/…/essence-dap-2O1w0G/Weather.js` in the
Debug Console — the JavaScript and the map you would otherwise never see.
`glueFrames: "subtle"` stops hiding the compiler's frames and greys them out
instead, which turns a two-frame stack inside `warmest` into nine.

`artifact` skips compiling altogether and debugs a bundle you already have,
with its `.map` beside it — a build from your release pipeline, say, rather
than one the adapter made. Breakpoints bind against whatever that map says.
Pointed at a bundle built without `--sourcemap`, every breakpoint comes back
unverified with the reason attached:

<div class="error-output">

```
the compiled bundle carries no source map
```

</div>

Pointed at an ordinary optimised build, breakpoints still bind and stops still
land — but the stack reads worse. A breakpoint on line 7 gives three frames in
an unoptimised bundle and four in an optimised one: the module's top level
loses its name, and Node's own `executeUserEntryPoint` arrives wearing a line
number out of your file, because a pass moved code the map still claims for
you. It is the right tool when the question is *does the optimised build do
this too*, and the wrong one to learn the debugger on.

<Note>
	`program` is the one required attribute as far as VS Code's schema is
	concerned, and the extension checks that it names a `.es` file that exists
	— unless `artifact` is set, in which case the bundle is the adapter's
	business and `program` is not consulted.
</Note>

</StepItem>

</Steps>

## Outside VS Code

The adapter knows nothing about VS Code. It is a DAP server on stdio, and the
command that starts it documents itself:

```sh
$ essence help dap

  essence dap — Start the Essence Debug Adapter, speaking over stdio

  USAGE

    essence dap

  DESCRIPTION

    Serves breakpoints, stepping, call stacks, variables and evaluation to an
    Editor over the Debug Adapter Protocol, reading requests from standard
    input and writing responses to standard output. Programs are compiled with
    this compiler before they are launched.

    This is started by an Editor rather than by hand: it prints nothing a
    person would want to read, and stays running until the debug session ends.
```

Any client that spawns that command and speaks the protocol at it gets the
same session VS Code gets. `esdap` is the same adapter under its own name,
linked by `bun install` the way `esls` is; the difference is only where
compiling comes from — `essence dap` hands the adapter the CLI's in-process
pipeline, while `esdap` spawns `essence build` for each launch.

What the adapter promises is a value in its own source rather than something
written inline into the handshake, so a client can read exactly what it will
get:

```json
{
  "supportsConfigurationDoneRequest": true,
  "supportsExceptionInfoRequest": true,
  "supportsEvaluateForHovers": true,
  "supportsDelayedStackTraceLoading": true,
  "supportsTerminateRequest": true,
  "exceptionBreakpointFilters": [
    { "filter": "uncaught", "label": "Uncaught Exceptions", "default": true },
    { "filter": "caught", "label": "Caught Exceptions", "default": false }
  ]
}
```

## The rough edges

Everything above works. These are the places where it is thinner than it looks,
and none of them is a bug report you need to file:

- **The console is JavaScript.** `coldest.degrees` answers, `::` does not.
  Watches and hover evaluation go through the same path, so an Essence
  expression in the Watch panel fails the same way.
- **You see what the compiled code captured.** A function literal only closes
  over what its body mentions, so evaluating a name from an enclosing function
  inside an inline callback can fail with `ReferenceError` while the same
  expression answers one frame up. The value is not hidden; it was never
  captured.
- **The runtime's own bindings show through.** The compiler's own names are
  filtered out of a scope, but the runtime helpers a bundle inlines are
  ordinary JavaScript ones, and they are not: `createInteger`, `unit`,
  `choiceIs` and a couple of dozen more. Inside a function that is the Closure
  scope, and Local is the one to read; at a module's own top level there is no
  Function to be local to, so the same names arrive in Local instead.
- **An anonymous function reads as `match`.** A function literal passed inline
  is named after the construct it is most often part of, so a callback written
  in place shows as `match` in the call stack. A named function — `warmer`
  above — carries its own name. The same fallback applies to the anonymous
  glue frames `glueFrames: "subtle"` reveals.
- **One thread, one request type.** There is no `attach`, no conditional
  breakpoints, no hit counts, no logpoints, no setting a variable from the
  Variables view, no restart-frame and no stepping backwards. The capability
  list above is the whole list.
- **Uncaught exceptions are rare, by design.** Two filters exist — Uncaught
  Exceptions, on by default, and Caught Exceptions, off — and a pause lands on
  the mapped line with the failure's own message. Neither fires often, because
  Essence expresses failure as a value: dividing by a possibly-zero Integer is
  an `Optional`, a square root of a negative is empty, and a `match` that does
  not cover its union is a diagnostic rather than a throw. The failure a clean
  program can reliably earn is a stack overflow, and that one does not pause:
  the `RangeError` arrives as program output and the session ends with it.
- **What you step is not what you ship.** The optimiser is off for the whole
  session, standard library included. If a program misbehaves only when
  optimised, the debugger will not show you why; turning one pass off with
  `--without-optimisation` on an ordinary build is the tool for that.
