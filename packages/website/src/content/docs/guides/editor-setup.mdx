An editor that understands Essence is not a second implementation of the
language. The Language Server runs the same parser, enricher and validator that
`essence check` runs, and formats through the same formatter `essence format`
uses, so a squiggle under a name and an error on the command line cannot
disagree about a program — they are the same code, reached two ways.

There is one editor integration in the repository: an extension for VS Code,
which bundles the server so nothing else has to be installed. Every other
editor gets the same server over the Language Server protocol, started as
`essence lsp`, and a client you configure yourself.

<Steps>

<StepItem title="Install the VS Code extension">

The extension is at `0.3.0`. It is not on the Marketplace and not on Open VSX,
so there is nothing to search for from inside VS Code — you install a `.vsix`.
A workflow in the repository builds one and attaches it to a GitHub release on
a `vscode-extension-v*` tag; no such tag has been cut yet, so building it out
of a checkout is the route that works today:

```sh
$ bun run --cwd packages/vscode-extension package
 DONE  Packaged: …/packages/vscode-extension/essence-language-0.3.0.vsix (34 files, 387.34 KB)
```

That script bundles the Language Server into `server/server.js`, copies the
standard library's `.es` sources beside it, bundles the extension itself into
`dist/extension.js`, and packs all of it into the `.vsix` — 34 files, and no
dependency on anything outside it. Install it the way VS Code installs any
local extension:

```sh
$ code --install-extension essence-language-0.3.0.vsix
Installing extensions...
Extension 'essence-language-0.3.0.vsix' was successfully installed.
```

The bundled server is a JavaScript file, and the extension spawns it as a child
process with `node`, so a `node` on PATH is all the language features need —
not Bun, and not a compiler checkout on the machine you edit on. Debugging
needs one thing more, the real `essence` CLI, which
[Debugging](/docs/guides/debugging) covers.

<Note>
	The extension activates on the first Essence file you open — until then it
	is inert, and the status bar shows nothing. Its manifest declares that it
	does not run in virtual workspaces (`github.dev` and its kind), and that in
	a workspace you have not trusted it keeps the language features on, because
	the server only reads and analyses text; the two settings that name an
	executable to spawn are the ones it gives up there.
</Note>

Open the folder rather than the single file. The server keys its cross-file
work — references, workspace-wide rename, workspace symbols, and the
`import { … }` edit that completion writes — off the workspace folders the
editor sends it at startup. A lone file outside every folder still gets
everything that fits in one file, and nothing that does not.

</StepItem>

<StepItem title="Watch it answer">

Put this in `lights.es` and open it:

<CodeWindow
	title="lights.es"
	class="code-bare"
	compact
	code={`implementation {

	choice Light {
		Red,
		Amber,
		Green,
	}

	§§ Whether a driver arriving at this Light has to stop.
	§§ @param light — the Light as it is showing now.
	§§ @returns — true for every Light that is not Green.
	function waiting(_ light: Light) -> Boolean {
		<- match light -> Boolean {
			case #Red { <- true }
			case #Green { <- false }
		}
	}

	constant crossing = waiting(#Red)

	Terminal.print(crossing)
}`}
/>

Four things should happen, and each one is a different part of the server
answering.

The `match` is underlined about 200ms after you stop typing, and the Problems
panel carries the code alongside the message:

<div class="error-output">

```
This Match Expression does not handle every Case: this is a Light
Note: Unhandled: 'Light#Amber'.
Help: Add 'case Light#Amber', or a 'case _' that covers the rest.
```

</div>

`missing-case` is that diagnostic's stable code — the same one
[the reference](/docs/reference/diagnostics) documents, and the same one
`essence check` prints. The message is the compiler's own, flattened onto the
squiggle: what the CLI draws as labels under a span arrives here as the notes
below the first line.

The lightbulb on that line (`Ctrl+.`) offers **Add missing cases**, which
inserts

```essence
			case Light#Amber {}
```

The body is left empty deliberately. Accepting the fix trades one Error for
another — `missing-return`, "Not every path through this function returns" —
and that second Error is the hole you were meant to fill. A Quick Fix here
scaffolds; it does not guess what your case should do.

Hovering `waiting` shows the signature and the `§§` block underneath it,
rendered rather than reprinted:

```
function waiting(_ Light) -> Boolean
```

> Whether a driver arriving at this Light has to stop.
>
> **light** — the Light as it is showing now.
>
> **Returns** — true for every Light that is not Green.

And `constant crossing` — written without a type — carries a faint `: Boolean`
after its name. That is an inlay hint, and double-clicking it writes `: Boolean`
into the source at exactly that position. The same edit is offered as a
refactoring under the lightbulb.

</StepItem>

<StepItem title="Know the settings">

The extension contributes four settings, and no more:

<div class="table-scroll">

| Setting | Default | What it does |
| --- | --- | --- |
| `essence.server.path` | `""` | Absolute path to a Language Server to run instead of the bundled one. A `.js`, `.cjs` or `.mjs` file is run with `node`; anything else is treated as source and run with `bun`. |
| `essence.inlayHints.enabled` | `true` | Show inferred types as inlay hints where the source states none. |
| `essence.trace.server` | `"off"` | Log the traffic between VS Code and the server. `"messages"` or `"verbose"`. |
| `essence.cli.path` | `""` | Absolute path to the `essence` CLI the debugger compiles with. Empty, a checkout open in the workspace is used if one is found, and `essence` on PATH otherwise. |

</div>

`essence.inlayHints.enabled` is the one setting the server itself reads: it
pulls the value over `workspace/configuration` and refreshes the hints in every
open editor when it changes, without a restart and without an edit.
`essence.trace.server` is applied live by the client. `essence.server.path` is
the only one that needs the server restarted, and changing it asks you whether
to restart there and then.

`essence.server.path` and `essence.cli.path` both name an executable to spawn,
which is why workspace-scoped values of them are ignored in a workspace you
have not trusted — a repository could otherwise point either at a program it
ships itself.

The extension also sets six editor defaults for Essence files, matching what
the formatter assumes rather than asking you to configure them:

<div class="table-scroll">

| Default | Value |
| --- | --- |
| `editor.insertSpaces` | `false` |
| `editor.tabSize` | `4` |
| `editor.detectIndentation` | `false` |
| `editor.rulers` | `[]` |
| `editor.defaultFormatter` | `essence.essence-language` |
| `editor.semanticHighlighting.enabled` | `true` |

</div>

Tabs, four wide, with detection off so the width is the one the formatter
measures against rather than the one guessed from the file. `editor.rulers` is
set to an empty list, which clears a ruler configured globally for Essence
files rather than adding one. And Format Document runs the extension itself —
the same formatter as `essence format`, in the server rather than as a second
process.

Snippets come with the extension too, one per construct: `implementation`,
`declarations`, `constant`, `variable`, `function`, `overload`, `namespace`,
`protocol`, `choice`, `choice-generic`, `type`, `type-record`, `record`,
`match`, `case`, `case-where`, `if`, `ifelse` and `doc`.

</StepItem>

<StepItem title="Find the server when it stops answering">

The extension registers exactly one command,
**Essence: Restart Language Server**, and puts it on a status bar item at the
right that appears as soon as an Essence file is open. The item spins while the
server is starting, shows a tick while it is running, and an error icon when it
has stopped or failed to start. Its tooltip names which server is running and
what it was run with — the bundled one, or the one `essence.server.path`
points at — which is the fastest way to find out that you are testing the wrong
binary. Clicking it restarts the server; so does the command.

The `Essence` channel in the Output panel carries the rest: a line at every
start naming the server, the client's own log, and the text of any failure. A
failure is also shown as a notification with a **Show Output** button, because
the detail worth reading is rarely the first line.

Two failures have a fix worth knowing. If the bundled server is missing —
which happens in a development checkout, where `server/` is a build product and
is not committed — the answer is `bun run build` inside
`packages/vscode-extension`. If `essence.server.path` points at something that
does not exist, or at something the machine cannot run, the message says so and
names the path; clearing the setting falls back to the bundled server.

That setting is also the loop for working on the server itself. Pointed at a
checkout's `packages/language-server/bin/esls`, it runs the server's TypeScript
directly under Bun, so a change to the server needs no bundling step at all:
**Essence: Restart Language Server** picks it up, without reloading the
window. The setting spawns what it names with `--stdio` and nothing else,
so it wants that launcher rather than the `essence lsp` command a terminal
would use.

</StepItem>

<StepItem title="Wire up an editor that is not VS Code">

The server speaks LSP over stdio and knows nothing about VS Code. The
toolchain exposes it as a command:

```sh
$ essence help lsp

  essence lsp — Start the Essence Language Server, speaking over stdio

  USAGE

    essence lsp

  DESCRIPTION

    Serves Diagnostics, hovers, completions, definitions, references, renames
    and formatting to an Editor over the Language Server Protocol, reading
    requests from standard input and writing responses to standard output.

    This is started by an Editor rather than by hand: it prints nothing a
    person would want to read, and stays running until the Editor closes the
    connection. Whatever arguments the Editor's client passes are left for the
    Server to read.
```

`esls` is that same server under its own name. Its launcher belongs to the
Language Server package rather than to the CLI, and `bun install` links it, so
inside a checkout `bun run esls` — or `packages/language-server/bin/esls`
directly — starts the server without going through the CLI at all. Either
route is one process speaking one protocol; which you point a client at is a
question of what is on PATH.

What a client has to be told is short:

- **Command** — `essence lsp`, or `esls`. Arguments the client adds are passed
  through untouched. If it passes no transport argument at all, the server
  appends `--stdio` itself rather than failing, so `essence lsp` on its own is
  a working server.
- **Files** — the `.es` extension, under a language id of `essence`. Untitled
  and never-saved buffers are served as well as files on disk.
- **Workspace folders** — send them. Everything that crosses a file boundary
  is built off them, and a client that sends none gets a per-file server.
- **Configuration** — the server asks for `essence.inlayHints.enabled` through
  `workspace/configuration`. A client that answers nothing keeps the hints, so
  there is no configuration to write to get the default.

The server registers its own file watcher for `**/*.es` dynamically, so a
client that supports `workspace/didChangeWatchedFiles` will keep the module
graph correct across a branch switch or a file written by another tool.
Diagnostics are pushed rather than pulled, and are debounced by roughly 200ms
after a change.

<Note>
	Nothing in the repository configures Neovim, Helix or Zed for you, and no
	such configuration is tested. What is tested is the server: it answers the
	same nineteen capabilities to any client that completes the handshake, VS
	Code's included.
</Note>

</StepItem>

</Steps>

## What the Language Server answers

The capabilities the server announces are a value in its own source rather than
something written inline into the handshake, precisely so that a feature cannot
quietly stop being advertised while its handler still passes every test.
Nineteen keys come back from `initialize`, and the first row below is the one
thing the server answers that is not among them: Diagnostics are pushed at the
editor rather than asked for, so nothing has to be advertised for them to
arrive.

<div class="table-scroll">

| Feature | Request | What you get |
| --- | --- | --- |
| Diagnostics | `publishDiagnostics` | Parser, enricher and validator findings as you type, each with a stable code, pushed about 200ms after you stop. |
| Quick Fixes | `codeAction` | Mechanical fixes keyed off the diagnostic code, plus writing an inferred type out as a refactoring. |
| Go to definition | `definition` | The declaration of any name that resolves — methods, namespace properties and Record members included. |
| Find all references | `references` | Every use of a name, across every file in the workspace. |
| Document highlight | `documentHighlight` | The occurrences in this file, distinguishing the ones that write a name from the ones that read it. |
| Rename | `rename`, `prepareRename` | A workspace-wide rename covering methods, Record members and the argument labels a parameter declares. |
| Linked editing | `linkedEditingRange` | The other occurrences of a name follow the one you are typing, without invoking rename. |
| Hover | `hover` | The inferred type of any expression, the full signature of a function or method, and its `§§` documentation rendered. |
| Completion | `completion` | Names in scope, members after `.`, methods after `::`, namespaces after `::<`, cases after `#` — inserted as the whole call, with the `import` edit that makes it resolve. |
| Signature help | `signatureHelp` | The invoked signature with the active parameter advancing as you type, one entry per overload. |
| Inlay hints | `inlayHint` | Inferred types where the source states none; double-clicking one writes it in. |
| Semantic tokens | `semanticTokens/full` | Every Identifier classified by what it resolves to, which a TextMate grammar cannot determine. |
| Outline | `documentSymbol` | Declarations with their types, reaching inside functions and `if` blocks; Namespaces expand to their members. |
| Workspace symbols | `workspace/symbol` | The same entries, searchable across files that are not open. |
| Call hierarchy | `prepareCallHierarchy` | What calls a function or method and what it calls. |
| Folding | `foldingRange` | Regions folded on the parser's structure rather than on indentation. |
| Selection ranges | `selectionRange` | Expand-selection that grows through the syntax tree. |
| Formatting | `formatting` | The whole document, through the same formatter `essence format` runs. |
| Workspace folders | `workspace` | Folder changes tracked, and `**/*.es` watched for changes made outside the editor. |
| Document sync | `textDocumentSync` | The whole text of a document on every change. Requests are answered off a fresh parse of it rather than off a tree kept between them. |

</div>

## What is not there

Worth knowing before you go looking for it:

- **Call hierarchy stops at the file.** It resolves against the document it was
  asked about, so a caller in another module does not appear.
- **There is no Fix All.** Not one of the Quick Fixes is both unambiguous and
  meaning-preserving, so applying them in bulk is deliberately not offered.
- **Formatting is whole-document only.** There is no range formatting and no
  format-on-type. The request is always for the whole file, though the edit
  that comes back is pared down to the span that actually changed.
- **Renaming a file does not follow its imports.** Nothing is announced for
  workspace file operations, so moving or renaming a `.es` file leaves every
  `import … from "./old.es"` naming it — and the watcher then reports each of
  them as unresolved, which is at least how you find them.
- **Go to type definition, go to implementation, code lenses, document links
  and type hierarchy are not implemented.** Nothing is announced for them, so
  an editor will not offer them.
- **Semantic tokens are re-sent whole.** No deltas, and no range request.

Two behaviours are surprising rather than missing. A diagnostic can
appear in a file you have not opened: an open file's analysis reaches its
imports, and what it finds there is published under the dependency's own URI —
open a module whose dependency does not compile, and the dependency gets the
squiggle while the importer gets `dependency-has-errors`. And renaming refuses
in three places on purpose — inside a standard library source, on anything the
compiler declares as a builtin, and on a declaration that lives outside every
workspace folder, where the uses this server was never asked to index would be
left naming something that no longer exists. The first two refusals take
linked editing with them, since it resolves through the same gate.

When enrichment fails outright — a compiler bug rather than a type Error —
the features that need types degrade to the purely lexical index instead of
taking the server down with them. Completion and the outline keep working;
hovers stop.
