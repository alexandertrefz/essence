An Essence module compiles to a standalone ES module: the whole module graph
and the parts of the runtime it reaches, bundled into one file that imports
nothing. So a JavaScript codebase can already run Essence — `import` it and the
functions are there. What it cannot do on its own is *talk* to them. Every
Essence value but a function carries its type on a hidden Symbol, and that
Symbol is minted while the bundle is evaluated, so a `List` in there is not an
`Array`, and a plain `12n` handed to a function expecting an `Integer` is a
value the module has never seen.

`@essence-lang/client` is the package that closes that gap. It compiles a `.es`
file, imports the result, and puts a marshalling boundary between the two
languages: a `bigint` goes in and an Essence `Integer` arrives, an Essence
`Rational` comes out and an `EssenceRational` arrives. Most of this guide is
about that boundary — what each type becomes in each direction, and what
happens when a value has no honest spelling on the other side.

The compiler is on the npm registry; the client package is not there yet, so
everything below was run from inside a checkout, where the workspace resolves
`@essence-lang/client` for any directory under it.
[Installation](/docs/getting-started/installation) covers getting one.

<StepItem title="Load a module and call into it">

The module to call. It is deliberately made of the shapes that are interesting
at a boundary: a Record, a List, a choice, an `Optional`, a `Rational` and an
arbitrary-precision `Integer`.

<CodeWindow
	title="Pricing.es"
	class="code-bare"
	compact
	code={`implementation {

	type LineItem = { name: String, cents: Integer }

	choice Discount {
		None,
		Fixed { cents: Integer },
		Percentage { of: Rational },
	}

	type Order = {
		items: List<LineItem>,
		discount: Discount,
		note: Optional<String>,
	}

	namespace Order for Order {
		static of(items: List<LineItem>, discount: Discount) -> Order {
			<- { items = items, discount = discount, note = #Empty }
		}

		subtotal() -> Integer {
			<- @.items::reduce(startingWith 0, (total, item) {
				<- total::add(item.cents)
			})
		}

		total() -> Integer {
			<- priceAfter(@.discount, on @::subtotal())
		}

		noted(_ note: Optional<String>) -> Order {
			<- { items = @.items, discount = @.discount, note = note }
		}
	}

	function priceAfter(_ discount: Discount, on cents: Integer) -> Integer {
		<- match discount -> Integer {
			case #None       { <- cents }
			case #Fixed      { <- cents::subtract(@.cents) }
			case #Percentage {
				<- cents::multiply(with 1::subtract(@.of))::round()
			}
		}
	}

	function taxOn(_ cents: Integer, at rate: Rational) -> Rational {
		<- cents::multiply(with rate)
	}

	function labels(_ items: List<LineItem>) -> List<String> {
		<- items::map((item) { <- "{item.name} — {item.cents}" })
	}

	constant taxRate  = 19/100
	constant currency = "EUR"
}

export {
	Discount
	LineItem
	Order
	currency
	labels
	priceAfter
	taxOn
	taxRate
}`}
/>

And the JavaScript that uses it. `loadModule` takes the path to the `.es` file
and answers with the module; there is no build step in front of it and no
artifact to keep track of.

<CodeWindow
	title="use-pricing.js"
	class="code-bare"
	compact
	code={`import { EssenceRational, loadModule } from "@essence-lang/client"

let pricing = await loadModule("./Pricing.es")
let { Order, priceAfter, taxOn, labels, taxRate, currency } = pricing.exports

let items = [
	{ name: "Notebook", cents: 1250n },
	{ name: "Pencil", cents: 199n },
]

let order = Order.of({
	items,
	discount: { $case: "Discount#Percentage", of: new EssenceRational(1n, 10n) },
})

console.log(labels(items))
console.log(Order.subtotal(order), Order.total(order))
console.log(order.note, Order.noted(order, "gift wrapped").note)
console.log(priceAfter({ $case: "Discount#Fixed", cents: 200n }, 1449n))
console.log(currency, taxRate.toString(), taxOn(1449n, taxRate).toString())`}
/>

Four things in that output are worth naming.

`exports` is the module as ordinary JavaScript. A constant is a value, a
Function is a function, and a namespace is an object of its methods — nothing
on this side has to know Essence was involved. A constant is marshalled when it
is *read*, not when the module loads, so an export the boundary has no mapping
for throws where you read it rather than taking the whole module with it.

A namespace comes back as a plain object, so `Order.of(…)` reads the same as it
does in Essence. There is no `::` here, so an instance method takes its
receiver where a call can pass it — first. `Order.subtotal(order)` is
`order::subtotal()`.

Essence writes a label at every call site, so a function whose parameters all
carry one may be called either way: `Order.of(items, discount)` positionally,
or `Order.of({ items, discount })` with a single object whose keys are exactly
the labels. A missing or misspelled key is a mistake rather than a positional
call that happens to pass an object. (A function of one Record parameter is
positional whatever its label says — both readings take an object, and a Record
can hold any shape.)

And the module's body runs when it is loaded. A `.es` file is a program, not a
header; if it prints on the way past, you will see that during `loadModule`.
The bundle is cached under the hash of everything it was compiled from and by —
every `.es` source, the compiler's version, the standard library's sources and
the runtime's — so a second load of unchanged sources reads that file back
instead of compiling, and inside one process the program is evaluated once.
(What is deliberately *not* hashed is the compiler's own sources. Editing the
compiler inside a checkout does not move the hash, so an edit there wants a
cache directory of its own.) `timed.js` below is one `loadModule` against a
cache directory named on the command line, timed:

<CodeWindow
	title="timed.js"
	class="code-bare"
	compact
	code={`import { loadModule } from "@essence-lang/client"

let directory = process.argv[2]
let started = Bun.nanoseconds()

await loadModule("./Pricing.es", { cacheDirectory: directory })

console.log(\`\${Math.round((Bun.nanoseconds() - started) / 1e6)} ms\`)`}
/>

```sh
$ bun timed.js /tmp/essence-cache-a4t9
228 ms
$ bun timed.js /tmp/essence-cache-a4t9
74 ms
```

Both numbers are one machine's and move by tens of milliseconds between runs.
The ratio is the part that holds.

Where that file goes is decided in order: `ESSENCE_CLIENT_CACHE` if it is set,
then `$XDG_CACHE_HOME/essence/client`, then the platform's own cache directory
— `~/Library/Caches/essence/client` on macOS, which is where these runs went,
`%LOCALAPPDATA%\essence\client\Cache` on Windows and `~/.cache/essence/client`
otherwise. `loadModule`'s `cacheDirectory` option overrides all of them, which
is what `timed.js` passes.

Two more options go to the compiler rather than to the cache. `host` is a
`ModuleHost` — an object with one `readFile` — so a host holding unsaved text
compiles what it has rather than what is on disk, and `optimisation` is the
same `OptimiserOptions` the compiler's own `--no-optimise` sets. Both reach the
hash: the text a `host` answers with is hashed like any other source, and the
Optimiser's settings are hashed beside it, so one file compiled two ways is two
cached bundles rather than one wrong one.

</StepItem>

<StepItem title="Know what a value becomes">

This table is the whole of the mapping, and it is the part of the boundary
worth reading twice:

| Essence            | JavaScript                                             |
| ------------------ | ------------------------------------------------------ |
| `Integer`          | `bigint`                                               |
| `Rational`         | `EssenceRational`                                      |
| `String`           | `string`, normalised to NFC on the way in              |
| `Boolean`          | `boolean`                                              |
| `List<T>`          | `Array`                                                |
| `{ a: T }`         | a plain object, closed — an undeclared key is refused  |
| `Optional<T>`      | `T` or `undefined`                                     |
| a case of a choice | `{ $case: "Choice#Case", …payload }`                   |
| a union            | whichever arm the value is                             |

The two directions are not mirror images, and the asymmetry explains most of
what the boundary does. Coming **out**, a value says what it is — every Essence
value but a function carries its type — so nothing has to be told anything.
Going **in**, `7` could be an `Integer`, a `Rational` or an `Optional<Integer>`,
so what decides is the type the module *declared*, read off the export surface
the compiler produced. Every value is built against that type, member by
member, which is why an argument that does not fit is caught at the edge rather
than three methods deep.

A union is the clearest case of that asymmetry. Coming out there is nothing to
decide — the value says which arm it is. Going in, the arms are tried in the
order they were *declared* and the first that admits the value is the one it
becomes, so a `type Either = Optional<String> | Integer` reads `"7"` as the
`Optional<String>`, because that arm is written first rather than because
anything weighed the two. Overlapping arms are decided, not ambiguous.

`Rational` is where the mapping earns its keep. There is no JavaScript number
for `1/3`, so a Rational crosses as the pair of `bigint`s the runtime actually
holds, wrapped in an `EssenceRational` — a class rather than a plain pair,
because otherwise a Record with a `numerator` and a `denominator` would be
indistinguishable from one. Going the other way, a `number` is read for the
value it *holds* rather than the value its decimal spelling suggests:

<CodeWindow
	title="rationals.js"
	class="code-bare"
	compact
	code={`import { EssenceRational, loadModule } from "@essence-lang/client"

let { exports } = await loadModule("./Pricing.es")
let { taxOn, taxRate } = exports

console.log(taxRate.toString())
console.log(taxOn(1000n, new EssenceRational(19n, 100n)).toString())
console.log(taxOn(1000n, 0.19).toString())
console.log(taxOn(1000n, 0.19).toNumber())
console.log(taxOn(1000n, 19n).toString())`}
/>

```sh
$ bun rationals.js

190/1
427841964600197125/2251799813685248

```

`0.19` is not `19/100`. It is the dyadic rational the double actually stores,
and the boundary hands the module that rather than rounding to the fraction you
probably meant. `.toNumber()` is the lossy door back, offered because a host
reaching for it usually knows. A `bigint` is a whole Rational, which is why
`19n` goes in as `19/1` and `taxOn(1000n, 19n)` answers `19000/1`.

`Integer` is a `bigint` in both directions. A `number` is admitted going in
only where it is a *safe* integer — `2 ** 53` is refused even though a double
holds it exactly, because past that point one double stands for several whole
numbers and the module would be handed a value that had already lost which one
was meant.

A String is normalised to NFC on the way in, because String equality in Essence
is normalised — a composed `é` and a decomposed one are one value there, and
letting both spellings through would put two values into a module that insists
they are the same. Pass a decomposed name through `labels` and what comes back
is composed:

<CodeWindow
	title="nfc.js"
	class="code-bare"
	compact
	code={`import { loadModule } from "@essence-lang/client"

let { exports } = await loadModule("./Pricing.es")

let composed = "café"
let decomposed = composed.normalize("NFD")
let [label] = exports.labels([{ name: decomposed, cents: 1n }])

console.log(composed.length, decomposed.length, label.length, label.includes(composed))`}
/>

```sh
$ bun nfc.js
4 5 8 true
```

Five code points went in, and the label that came back is eight long — four for
the name, four for `" — 1"` — and contains the composed spelling, not the one
that was passed.

A case of a choice is a plain object carrying its own tag under `$case`,
spelled as the choice was *declared* — `Discount#Percentage`, never the path of
the machine that compiled it. Going in, the bare case name works too, so
`{ $case: "Percentage", of: 0.1 }` reaches the same case. `Optional` is the
exception: it is spelled by its absence, `T | undefined`, and
its cases never appear. `null` is admitted beside `undefined` on the way in,
since JSON has only the one of them, and `undefined` is what comes back. The
one case that has no spelling at all is one whose payload declares a member
actually named `$case`: the tag would sit on top of it, so the case is refused
in both directions rather than quietly losing the member.

</StepItem>

<StepItem title="Read the refusals">

A boundary that quietly accepted a value it could not carry would be worse than
no boundary, so the client refuses instead, and says where. Four Error classes,
told apart by whose mistake they are:

| Error                  | What went wrong                                     |
| ---------------------- | --------------------------------------------------- |
| `EssenceCompileError`  | The Essence source did not compile.                 |
| `EssenceMarshalError`  | A value does not fit the type on the other side.    |
| `EssenceCallError`     | The call itself — wrong count, wrong labels.        |
| `EssenceBuildError`    | The build is set up in a way that cannot work.      |

<CodeWindow
	title="errors.js"
	class="code-bare"
	compact
	code={`import { loadModule } from "@essence-lang/client"

let { exports } = await loadModule("./Pricing.es")
let { Order, priceAfter, labels } = exports

function show(work) {
	try {
		console.log("ok:", work())
	} catch (error) {
		console.log(\`\${error.name}: \${error.message}\`)
	}
}

show(() => labels([{ name: "Pencil", cents: "199" }]))
show(() => labels([{ name: "Pencil", cents: 199n, sku: "P-1" }]))
show(() => priceAfter({ $case: "Discount#Fixed", cent: 200n }, 1449n))
show(() => priceAfter({ $case: "Discount#Fixed", cents: 200n }))
show(() => Order.of({ items: [], discounts: { $case: "Discount#None" } }))`}
/>

```sh
$ bun errors.js

EssenceMarshalError: argument 1 → [0]: expected { name: String, cents: Integer }, got an object with a member it does not declare — 'sku'.
EssenceMarshalError: argument 1: expected Discount#Fixed, got an object with a member it does not declare — 'cent'.
EssenceCallError: priceAfter(_ Discount, on: Integer) -> Integer takes 2 Arguments; 1 Argument was passed.

It was passed one object with 'items', 'discounts'.
```

A marshalling failure names the path from the argument down to the value that
did not fit — `argument 1 → [0].cents` — and carries that same path on the
Error as `.path`, so a host can group or point at a failure without parsing the
sentence. A Record is **closed**: a key the type does not declare is a
misspelling in the making, and taking it silently is how a `widht` reaches
production.

A call failure names the signature and both ways of writing a call to it,
because whoever got one wrong is reading it to find the other.

`loadModule` on a source that does not compile throws an `EssenceCompileError`
whose message is the report `essence check` prints — the excerpt, the
underline, the Notes and the tally, one block per file, rendered against that
file's own source:

The diagnostics themselves are on the Error as `.diagnostics`, each with its
code, so a build can group by code without reading any prose. The message is

terminal — and `renderGroups(error.diagnosticGroups, true)` renders it again in
colour for a host that knows it is writing to one.

<StepItem title="Give a TypeScript caller the types">

`generateDeclarations` turns a module's export surface into a TypeScript
declaration file. It is the same mapping as the table above, read as types
rather than as values, which is what makes the declaration and the marshaller
one boundary instead of two descriptions of one. It takes three options:
`view`, which is `javascript` here and `bundle` in the next step;
`moduleName`, which only names the source in the header; and
`clientSpecifier`, for a generated file that has to reach `EssenceRational`
from somewhere the package name does not resolve.

<CodeWindow
	title="declare.js"
	class="code-bare"
	compact
	code={`import { writeFile } from "node:fs/promises"

import { generateDeclarations, loadModule } from "@essence-lang/client"

let pricing = await loadModule("./Pricing.es")

await writeFile(
	"Pricing.d.ts",
	generateDeclarations(pricing.surface, { moduleName: "Pricing.es" }),
)`}
/>

```ts
// Generated from Pricing.es by @essence-lang/client. Do not edit.
//
// The Module as JavaScript — what `loadModule(…).exports` answers with.

import type { EssenceRational } from "@essence-lang/client"

export type Discount =
	| { $case: "Discount#None" }
	| { $case: "Discount#Fixed"; cents: bigint }
	| { $case: "Discount#Percentage"; of: EssenceRational }

export type LineItem = { name: string; cents: bigint }

export type Order = {
	items: Array<LineItem>
	discount: Discount
	note: string | undefined
}

export declare const Order: {
	of(items: Array<LineItem>, discount: Discount): Order
	subtotal(p0: Order): bigint
	total(p0: Order): bigint
	noted(p0: Order, p1: string | undefined): Order
}

export declare const currency: string
export declare function labels(p0: Array<LineItem>): Array<string>
export declare function priceAfter(p0: Discount, on: bigint): bigint
export declare function taxOn(p0: bigint, at: EssenceRational): EssenceRational
export declare const taxRate: EssenceRational
```

A type alias is declared under the name it was written with and referred to by
it everywhere else, a choice becomes the union of its cases, and `Optional<T>`
is `T | undefined`. A parameter is named by its label — `on`, `at` — and a `_`
Parameter by its position, `p0`. Put that file beside a `Pricing.js` that
TypeScript will never actually find, and a caller reads the module's types off
the declaration while `loadModule` supplies the values:

<CodeWindow
	title="typed.ts"

let { Order, labels } = pricing.exports as unknown as Pricing

let order = Order.of([{ name: "Pencil", cents: 199n }], { $case: "Discount#None" })

console.log(labels(order.items), Order.total(order), order.note?.length)`}
/>

	title="tsconfig.json"

	code={`{

		"moduleResolution": "bundler",

Two things the declaration is not. It describes the *positional* call only, so
the labelled-object form that works at runtime does not typecheck — pass the
Arguments in order from TypeScript. And it is stricter than the marshaller
about numbers: `cents: 199` runs, because a safe integer is admitted, but the
declaration says `bigint` and TypeScript refuses it. Both are the conservative
direction, which is the one a generated file should err in.

What the boundary cannot carry is declared `never` rather than spelled out,
because a declaration is only worth having if the calls it admits are the calls
that work. A callback parameter is `never`, and so is a type parameter in an
input position — a type parameter is a shape that has not been decided yet, and
a value going *in* has to be built against a shape. A type parameter in the
*return* position stays a TypeScript one, because nothing has to be built
there. Three functions that reach all three edges —

<CodeWindow
	title="Limits.es"
	class="code-bare"
	compact
	code={`implementation {

	function deep(_ value: Optional<Optional<Integer>>) -> Boolean {
		<- value::hasValue()
	}

	function firstOf<ItemType>(_ items: List<ItemType>) -> Optional<ItemType> {
		<- items::firstItem()
	}

	function mapped(
		_ items: List<Integer>,
		with transform: (_: Integer) -> Integer,
	) -> List<Integer> {
		<- items::map(transform)
	}
}

export {
	deep
	firstOf
	mapped
}`}
/>

— and the declarations they generate:

```ts
export declare function deep(p0: bigint | undefined | undefined): boolean
export declare function firstOf<ItemType>(p0: Array<never /* a Type Parameter can not be marshalled */>): ItemType | undefined
export declare function mapped(p0: Array<bigint>, p1: never /* callbacks are not supported yet */): Array<bigint>
```

And the same three refusals as the marshaller states them at runtime:

<CodeWindow
	title="limits.js"
	class="code-bare"
	compact
	code={`import { loadModule } from "@essence-lang/client"

let { deep, firstOf, mapped } = (await loadModule("./Limits.es")).exports

function show(work) {
	try {
		console.log("ok:", work())
	} catch (error) {
		console.log(\`\${error.name}: \${error.message}\`)
	}

show(() => firstOf([1n, 2n]))

```sh
$ bun limits.js
EssenceMarshalError: argument 1: an Optional inside an Optional has no JavaScript spelling — both levels would be 'undefined', and '#Value(#Empty)' is not '#Empty'.
EssenceMarshalError: argument 1 → [0]: ItemType is a Type Parameter — there is no shape to build a value against until it is applied.

```

The `ok: undefined` is `firstOf([])` — an empty Array is the one value that
gets through a type parameter, because there is nothing in it to build. The
nested `Optional` is the one gap the declaration does not cover: `deep` is
declared `bigint | undefined | undefined`, which collapses to two levels of
nothing TypeScript is happy to typecheck and the marshaller then refuses. Read
that as a rough edge, not as a promise.

</StepItem>

<StepItem title="Compile inside a bundler">

`loadModule` compiles at load time, which means the compiler has to be there at
run time. For anything you ship — a browser bundle above all — the compile
belongs in the build, and that is what the plugins are for. `essence()` is a
Vite plugin and `essenceEsbuild()` an esbuild one; both compile an imported
`.es` file where the bundler asks for its text, and hand back one standalone
Module the host bundler has nothing left to resolve.

<CodeWindow
	title="build.js"
	class="code-bare"
	compact
	code={`import * as esbuild from "esbuild"

await esbuild.build({
	entryPoints: ["app.js"],
	bundle: true,
	format: "esm",
	outfile: "dist/app.js",

The esbuild driver says nothing when it succeeds and leaves `dist/app.js`. The
`--bun` on the second is not decoration: a plain `bun run vite` hands the
config file to Node, which cannot resolve the workspace's TypeScript and fails
before the plugin is ever asked for anything.

What the build then holds is the **bundle's** exports, not the marshalled ones:
Essence's own values, under the names the rewriter emitted them as. The
marshaller cannot come along — it reads types out of an export surface and
prints its errors with the compiler's own printer, so shipping it would ship
the compiler. What ships instead is the *bridge*: the bundle's own type key and
value constructors, exported beside the module's names.

<CodeWindow
	title="app.js"
	class="code-bare"
	compact
	code={`import {
	labels,
	priceAfter,
	$bridge_case,
	$bridge_integer,
	$bridge_list,
	$bridge_record,
	$bridge_string,
} from "./Pricing.es"

let items = $bridge_list([
	$bridge_record({
		name: $bridge_string("Notebook"),
		cents: $bridge_integer(1250n),
	}),
])

console.log(labels(items))
console.log(
	priceAfter(
		$bridge_case("./Pricing.es#Discount#Fixed", {
			cents: $bridge_integer(200n),

	),
)`}

That is the honest shape of the bundler path: values in and out are Essence's,
opaque, and building one takes a bridge constructor. A case tag there is
qualified by the module it was declared in, spelled relative to the entry —
`./Pricing.es#Discount#Fixed`. Marshal at the edge of your own code, or reach
for `loadModule` where you can afford to compile at load time.

While a dev server is serving, the Vite plugin writes a `<Name>.d.es.ts` beside
each compiled file — which is where TypeScript looks for the declarations of a
`.es` import under `allowArbitraryExtensions`. It is the same generator in its
`bundle` view, so it declares what is really there, `EssenceValue` and all,
along with the bridge — three lines out of the `Pricing.d.es.ts` that build
wrote:

```ts
type EssenceValue = object

export declare function labels(p0: EssenceValue): EssenceValue
export declare const $bridge_integer: (value: bigint) => EssenceValue
export declare const $bridge_list: (items: Array<EssenceValue>) => EssenceValue
```

`declarations` turns that on in a build or off in a server; under esbuild it is
off unless you ask. It is one of three options both plugins take — the other
two are the `host` and the `optimisation` `loadModule` takes, and mean the same
thing here. The types it buys are thin by construction: every value is
`EssenceValue`, so nothing checks that the value you passed is the one the
Parameter wanted. What it does buy is the export list and the arity, which is
enough for TypeScript to catch `labels()` with no argument at all.

<Note>
	**One `.es` entry per build.** Each entry compiles to its own standalone
	bundle, with its own copy of the runtime and its own hidden type key — so a
	value built by one is not recognised by the other, and a `match` on it would
	take the wrong case rather than fail. Importing two `.es` files that reach a
	common source is refused for that reason.
</Note>

## The whole surface

The twenty-three values `@essence-lang/client` exports today:

| Name                                                     | What it is                                                 |
| -------------------------------------------------------- | ---------------------------------------------------------- |
| `loadModule`                                              | A path to a `.es` file in, the module out.                 |
| `EssenceRational`                                         | A Rational as JavaScript holds it.                         |
| `generateDeclarations`                                    | An export surface as a TypeScript declaration file.        |
| `essence`, `essenceEsbuild`                               | The Vite and esbuild plugins.                              |
| `EssenceCompileError`, `EssenceMarshalError`, `EssenceCallError`, `EssenceBuildError` | The four refusals.      |
| `renderGroups`                                            | A compile Error's report, rendered again in colour.        |
| `createMarshaller`, `bindModule`                          | The boundary and the binding, for a host building its own. |
| `runtimeBridgeOf`, `withRuntimeBridge`                    | The bridge, read off a bundle or added to one.             |
| `BRIDGE_EXPORTS`, `BRIDGE_KEY`, `BRIDGE_SPECIFIER`        | The names and cache key the bridge is spelled by.          |
| `cacheDirectory`, `bundlePath`, `cacheBundle`, `cachedBundle` | The bundle cache, if you want to drive it yourself.    |
| `declarationsPath`                                        | Where a `.d.es.ts` goes for a given `.es` file.            |
| `escapeName`                                              | An Essence name as the rewriter emits it.                  |

The types that spell those signatures are exported beside them — `EssenceModule`
and `LoadOptions`, `Marshaller`, `RuntimeBridge`, `PluginOptions`,
`DeclarationOptions` — and so are the compiler's own `ExportSurface`,
`ModuleHost`, `OptimiserOptions` and `DiagnosticGroup`, re-exported here so that
a host can name what this package handed it without taking a dependency on the
compiler.

The plugins are also reachable one door over, at
`@essence-lang/client/vite-plugin` and `@essence-lang/client/esbuild-plugin`,
which is the import a build config usually wants.

## What it does not do yet

- **Callbacks.** A function cannot be passed *in*: a parameter that takes one
  is refused at the boundary and declared `never`. One that comes *out* is
  handed over exactly as the bundle holds it — it takes and answers that
  bundle's own values, so calling it means building them through `bridge`, and
  the declaration, which spells it as an ordinary JavaScript function, promises
  more than the boundary delivers.
- **Generics.** An argument at a type parameter position is refused, and only
  an empty `List` gets through. A generic function is still callable through
  `raw`, where nothing is marshalled.
- **Overloads.** A JavaScript value carries no type, so nothing at the boundary
  can decide which overload a call means; each is reached by its own name on
  `raw`. No module you write can hit this today — `overload function` is the
  standard library's alone.
- **Nested Optionals.** `Optional<Optional<T>>` is refused in both directions
  rather than collapsed into the one level JavaScript can spell.
- **The numeric tower above `Rational`.** An `Algebraic` or a `Transcendental`
  has no JavaScript to be, and is refused rather than rounded. Because a
  constant is marshalled on read, the refusal lands on the export that caused
  it and the rest of the module stays reachable — a module exporting both
  `constant root = 2::squareRoot()` and `constant plain = 7` reads `7n` for one
  and throws `EssenceMarshalError: root: Algebraic values can not be marshalled
  yet.` for the other.
- **Checked refinements.** A refined type marshals as its base, unproven. The
  predicate belongs at the boundary and is not run there yet.
- **Compiling in a browser.** The compiler reads files and shells out to
  esbuild. What a browser runs is the output, which is what the plugins are for.
